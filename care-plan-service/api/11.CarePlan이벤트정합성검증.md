# 11. CarePlan 이벤트 정합성 검증 — `serviceResultId` 교차 검증 구현 결과

> 관련 이슈: [Feat] CarePlan 이벤트 발행·소비 안정성 및 정합성 개선 #283
>
> **문서 상태: 구현 완료 (2026-09-13).** 1~9장은 구현 전 현황을 분석한 원본 내용을 그대로 남겨 두었고(왜 이 검증이 필요했는지 이해하는 데 필요), 10장부터 실제 구현 결과를 반영했다. 코드가 우선이며, 실제 구현과 아래 분석이 다른 경우 실제 코드가 맞다. 이번 구현 범위는 `carePlanId` 교차 검증 하나뿐이며, 9장에서 "기술 부채"로 분류한 장기간 `IN_PROGRESS` 탐지와 `12.Outbox운영안정성.md` 범위(Outbox FAILED 운영/다중 인스턴스)는 이번에도 손대지 않았다.

## 1. `CarePlanCompleted` 이벤트 payload 구조

```java
// careplan/application/event/CarePlanCompletedEvent.java
public record CarePlanCompletedEvent(
        UUID carePlanId,
        UUID serviceResultId,   // CANCELED일 때는 null 허용 (validateCompletedEvent 참고)
        ScheduleStatus status   // SCHEDULED, RESCHEDULING, CHANGED, COMPLETED, CANCELED, NO_SHOW
) {
}
```

이 이벤트는 schedule-service가 발행하고, care-plan-service의 `CarePlanEventConsumer`가 수신한다(자세한 소비 흐름은 `10.CarePlanCompleted이벤트소비.md` 참고).

## 2. `serviceResultId`로 Schedule Service를 조회하는 현재 흐름

```
CarePlanCommandService.completeCarePlan(event)
   └─ event.serviceResultId() != null 이면
        scheduleResultQueryPort.findById(event.serviceResultId())
             │
             ▼
        ScheduleResultClientAdapter.findById(serviceResultId)
             │
             ├─ scheduleFeignClient.findServiceResult(serviceResultId)
             │       GET /internal/v1/service-results/{serviceResultId}
             │       → ScheduleInternalResponse {
             │             success, code, message,
             │             data: { serviceResultId, carePlanId }   ← 응답에 carePlanId가 이미 포함됨
             │         }
             │
             └─ return new ScheduleResultFindResult(
                      scheduleInternalResponse.data().serviceResultId()
                      // ⚠ data().carePlanId()는 응답에 존재하지만 여기서 읽지 않고 버려짐
                )
```

관련 파일:

- `careplan/application/port/ScheduleResultQueryPort.java` — `findById(UUID serviceResultId): ScheduleResultFindResult`
- `careplan/infrastructure/adapter/ScheduleResultClientAdapter.java` — 위 흐름의 실제 구현
- `careplan/infrastructure/client/ScheduleFeignClient.java`, `ScheduleInternalResponse.java`
- `careplan/application/result/ScheduleResultFindResult.java` — **`serviceResultId` 필드 하나만 존재**

## 3. 현재 어떤 값까지 검증하고 있는가

`CarePlanCommandService.completeCarePlan()` 기준으로 실제 검증되는 항목은 다음 세 가지뿐이다.

1. `validateCompletedEvent(event)` — `status != CANCELED`인데 `serviceResultId == null`이면 거부(`CARE_PLAN_COMPLETED_EVENT_INVALID`).
2. `serviceResultId != null`일 때 `scheduleResultQueryPort.findById(serviceResultId)` 호출이 **예외 없이 성공하는지** — 즉 "그 ID의 수행 결과가 schedule-service에 실제로 존재하는가"만 확인한다. 반환값(`ScheduleResultFindResult`)의 내용 자체는 이후 로직에서 전혀 사용되지 않는다(단순히 예외가 안 나면 통과).
3. `event.carePlanId()`로 `carePlanCommandRepository.findById()`를 호출해 **해당 ID의 Care Plan이 존재하는지**만 확인한다(`CARE_PLAN_NOT_FOUND`).

**검증하지 않는 것:** "이벤트에 실려온 `serviceResultId`가 실제로 이 `carePlanId`에 속한 수행 결과인가"는 어디에서도 확인하지 않는다. `ScheduleInternalResponse.Data`에는 `carePlanId` 필드가 이미 내려오는데(`careplan/infrastructure/client/ScheduleInternalResponse.java` 참고), `ScheduleResultClientAdapter`가 이를 읽지 않고 버리기 때문이다.

## 4. Schedule Service 응답의 `carePlanId`를 비교하지 않을 경우 발생 가능한 문제

**현재 구조 →** `completeCarePlan()`은 "이벤트의 `carePlanId`로 조회한 Care Plan"과 "이벤트의 `serviceResultId`로 조회한 수행 결과가 존재하는지" 두 가지를 **서로 독립적으로만** 확인하고, 두 값이 실제로 짝이 맞는지는 확인하지 않는다.

**문제 발생 조건 →** 이벤트의 `carePlanId` 필드와 `serviceResultId` 필드가 서로 다른 Care Plan에 속하는 상황이 발생하면(예: schedule-service 측 이벤트 발행 로직의 버그로 잘못된 `carePlanId`가 실린 경우, 메시지 큐 재처리/리플레이 과정에서 오래된 이벤트가 다른 Care Plan에 잘못 매칭되는 경우, 혹은 내부망에서 큐에 직접 접근해 조작된 메시지가 발행되는 경우) — `serviceResultId`는 schedule-service에 실존하므로 2번 검증을 통과하고, `carePlanId`도 DB에 실존하는 Care Plan이므로 3번 검증도 통과한다. **두 조건 모두 개별적으로는 참이지만, 이 둘이 서로 관련 없는 데이터일 수 있다는 점을 코드가 확인하지 않는다.**

**영향 →**

- 실제로는 아직 완료되지 않은(또는 아예 관련 없는) Care Plan이 `COMPLETED` 상태로 전이된다.
- `CarePlan.canTransitionTo()`(`CarePlan.java`)를 보면 `COMPLETED`에서 되돌아가는 전이 경로가 정의되어 있지 않다 — 한 번 잘못 완료되면 애플리케이션 로직으로 되돌릴 방법이 없다.
- `carePlan.complete()`가 `true`를 반환하면 곧바로 `carePlanCompletionEventAppender.append(carePlan)`이 호출되어 `CarePlanCompletionEvent`가 Outbox에 적재되고, 결국 social-worker-service 등 후속 소비자에게도 "이 Care Plan이 완료되었다"는 잘못된 알림이 전파된다.
- 원인 추적도 어렵다 — 현재 로그(`CarePlanEventConsumer`의 info 로그)에는 `carePlanId`/`serviceResultId`/`status`가 남지만, 이 둘의 소유 관계 불일치를 감지하는 로직 자체가 없으므로 로그만으로는 문제가 있었는지조차 알 수 없다.

## 5. 교차 검증 추가 시 변경이 필요한 부분

DTO / Feign Client / Adapter / Command Service 각각에 필요한 변경은 다음과 같다.

| 계층 | 파일 | 필요한 변경 |
| --- | --- | --- |
| Feign Client | `ScheduleFeignClient.java` | **변경 불필요** — 이미 호출 중인 `GET /internal/v1/service-results/{serviceResultId}`가 응답에 `carePlanId`를 포함하고 있으므로 API 자체를 바꿀 필요가 없다. |
| 응답 DTO | `ScheduleInternalResponse.java` | **변경 불필요** — `Data record`에 `carePlanId`가 이미 정의되어 있다. |
| 내부 결과 DTO | `careplan/application/result/ScheduleResultFindResult.java` | **변경 필요** — 현재 `serviceResultId` 필드 하나뿐이므로 `carePlanId` 필드를 추가해야 한다. |
| Adapter | `careplan/infrastructure/adapter/ScheduleResultClientAdapter.java` | **변경 필요** — `scheduleInternalResponse.data().carePlanId()`를 읽어 `ScheduleResultFindResult`에 담아 반환하도록 수정. |
| Port | `careplan/application/port/ScheduleResultQueryPort.java` | 시그니처(`findById(UUID): ScheduleResultFindResult`) 자체는 그대로 유지 가능 — 반환 타입의 필드만 늘어나므로 인터페이스 변경은 불필요. |
| Command Service | `careplan/application/service/command/CarePlanCommandService.java` | **변경 필요** — `completeCarePlan()`에서 `scheduleResultQueryPort.findById(...)`의 반환값(`carePlanId`)과 `event.carePlanId()`를 비교하는 검증을 추가해야 한다. 현재 `validateCompletedEvent()`는 `// TODO : validate 분리 시급` 주석이 이미 달려 있어(`docs/technical-debt/IMPROVEMENTS.md` 4번 항목과 연계), 이 교차 검증을 추가하는 김에 별도 validator로 분리하는 것도 함께 검토할 만하다. |
| 에러 코드 | `global/exception/ErrorCode.java` | **변경 필요** — 불일치 시 던질 새 에러 코드(예: `CARE_PLAN_COMPLETED_EVENT_CARE_PLAN_MISMATCH`)가 필요하다. |

## 6. Care Plan Service가 Schedule Service의 완료 판단을 신뢰해야 하는 수준

- **신뢰해야 하는 것:** "이 `serviceResultId`가 실제로 schedule-service에 존재하고, 그 상태가 이벤트에 실린 `status`와 일치한다"는 사실 자체. 이는 스케줄이 실제로 어떻게 수행되었는지(방문 여부, 제공자의 실제 이행 여부 등)를 판단하는 schedule-service/provider-service의 도메인 책임 영역이며, care-plan-service가 이를 재검증할 도메인 지식도, 필요도 없다. 내부 API는 `InternalApiKeyInterceptor`(`FeignConfig`)로 보호되는 신뢰 경계 내부 호출이므로, "이 리소스가 실존한다"는 응답 자체는 신뢰할 수 있는 전제로 두는 것이 합리적이다.
- **재검증해야 하는 것:** "그 실존하는 리소스가 **이 이벤트가 주장하는 `carePlanId`에 속한 것인지**"는 별개의 질문이다. 이는 이벤트 payload 자체의 무결성(발행 로직의 버그, 메시지 조작/오배송 가능성)에 대한 문제이며, "행위자가 실존한다"는 것과 "그 행위가 이 자원에 속한다"는 것은 서로 다른 신뢰 축이다. 4장에서 설명한 문제는 바로 이 두 번째 축을 검증하지 않아서 발생한다.

정리하면, care-plan-service는 schedule-service가 "이 스케줄이 완료되었다"고 판단한 사실 자체는 신뢰하되, 그 완료 사실이 **이 이벤트가 완료 대상으로 지목한 Care Plan과 실제로 연결되어 있는지**는 이미 호출 중인 같은 API 응답 안에서 스스로 확인해야 한다.

## 7. Care Plan Service에서 검증 가능한 데이터 vs 검증 불가능한 데이터

| 구분 | 예시 | 검증 가능 여부 |
| --- | --- | --- |
| 이벤트 payload 자체의 구조적 유효성 | `serviceResultId`가 `CANCELED`가 아닐 때 null이 아닌지 (`validateCompletedEvent`) | 이미 검증 중 |
| `serviceResultId`의 실존 여부 | schedule-service에 해당 ID가 있는지 | 이미 검증 중 (Feign 호출 성공 여부) |
| `carePlanId`의 실존 여부 | care-plan-service DB에 해당 ID가 있는지 | 이미 검증 중 |
| **`serviceResultId`와 `carePlanId`의 소유 관계** | 응답의 `data.carePlanId`와 이벤트의 `carePlanId`가 같은지 | **검증 가능하지만 현재 하지 않음 — 이번 개선 대상** |
| 실제 서비스가 물리적으로 수행되었는지 | 제공자가 실제로 방문했는지, 서비스 품질 등 | care-plan-service가 검증 불가능 — schedule-service/provider-service의 책임 영역이며 care-plan-service에는 이를 판단할 데이터나 권한이 없음 |
| `status` enum 값 자체의 신뢰성 | schedule-service가 `COMPLETED`라고 보낸 것이 실제로 맞는지 | care-plan-service가 검증 불가능 — 6장에서 설명한 "신뢰해야 하는 부분"에 해당 |

## 8. 과도한 서비스 간 결합 없이 적용 가능한 최소 정합성 검증안

이미 호출하고 있는 `GET /internal/v1/service-results/{serviceResultId}` 응답에 `carePlanId`가 포함되어 있으므로, **새로운 API 호출이나 새로운 동기 의존성을 추가할 필요가 없다.** 필요한 것은:

1. `ScheduleResultFindResult`에 `carePlanId` 필드 추가 (기존 응답에서 이미 받고 있던 값을 버리지 않고 전달)
2. `CarePlanCommandService.completeCarePlan()`에서 `scheduleResultFindResult.carePlanId().equals(event.carePlanId())` 비교 후 불일치 시 예외

이 방식은 서비스 간 호출 횟수, 타임아웃 노출 지점, 장애 전파 경로를 전혀 늘리지 않으면서 이미 오가는 데이터를 한 번 더 확인하는 수준이므로, "과도한 결합"에 해당하지 않는다.

## 9. 장기간 `IN_PROGRESS` 상태에 머무는 Care Plan 탐지 — 구현 대상 여부

**기술 부채로 분류하고 이번 작업(#283)에서는 구현하지 않는다.**

근거:

- 현재 코드베이스 어디에도 `IN_PROGRESS` 상태의 체류 시간을 감시하는 배치/스케줄러/알림 로직이 없다(`CarePlanOutboxRelayScheduler`처럼 기존에 재사용할 만한 유사 스케줄러도 없음 — 있는 것은 Outbox 발행용 스케줄러뿐이며 목적이 다름).
- 이슈 #283의 "주요 개선 범위"는 이벤트 발행/소비의 안정성·정합성(Outbox, Retry/DLQ, 교차 검증)이며, "완료 이벤트가 아예 오지 않는 경우를 어떻게 탐지할 것인가"는 별개의 운영 모니터링 주제(배치 설계, 알림 채널, 임계값 정책 등 추가 논의가 필요)다.
- 이 탐지 기능이 있다면 "완료 이벤트 유실/오배송으로 인해 영원히 `IN_PROGRESS`에 머무는 Care Plan"을 사후에 잡아낼 수 있어 4장의 문제를 보완하는 안전망이 될 수 있지만, 지금 시점에 함께 설계/구현하기에는 범위가 커 별도 이슈로 분리하는 것이 타당하다.

## 10. 실제 구현 결과 — 영향받은 클래스와 실제 변경 내용

사전에 확인한 영향 범위(`ScheduleResultFindResult`, `ScheduleResultClientAdapter`, `CarePlanCommandService`) 그대로 수정했고, 그 외 추가로 변경이 필요했던 파일은 없었다.

| 파일 | 실제 변경 내용 |
| --- | --- |
| `careplan/application/result/ScheduleResultFindResult.java` | `carePlanId` 필드 추가 (`record ScheduleResultFindResult(UUID serviceResultId, UUID carePlanId)`) |
| `careplan/infrastructure/adapter/ScheduleResultClientAdapter.java` | `findById()`에서 `scheduleInternalResponse.data().carePlanId()`를 함께 담아 반환하도록 수정 (이미 응답에 존재하던 값을 더 이상 버리지 않음) |
| `careplan/application/port/ScheduleResultQueryPort.java` | **변경 없음** — 시그니처(`findById(UUID): ScheduleResultFindResult`)는 그대로 유지 |
| `careplan/application/service/command/CarePlanCommandService.java` | `completeCarePlan()`에서 `scheduleResultQueryPort.findById(...)`의 반환값을 지역 변수로 받아 신규 `validateCarePlanId(event, scheduleResultFindResult)` private 메서드로 교차 검증. 불일치 시 `BusinessException(CARE_PLAN_COMPLETED_EVENT_CARE_PLAN_MISMATCH)`를 던지며, 이 시점은 `carePlanCommandRepository.findById(...)` 호출보다 **앞**이므로 불일치 시 Care Plan 조회 자체가 일어나지 않는다 |
| `global/exception/ErrorCode.java` | `CARE_PLAN_COMPLETED_EVENT_CARE_PLAN_MISMATCH(HttpStatus.BAD_REQUEST, "완료 이벤트의 carePlanId와 Schedule 수행 결과의 carePlanId가 일치하지 않습니다.")` 추가 |

`validateCompletedEvent()`를 별도 validator 클래스로 분리하는 것(`docs/technical-debt/IMPROVEMENTS.md` 4번 항목)은 이번 작업 범위에 포함하지 않았다 — 이번에 추가한 `validateCarePlanId()`도 기존 `validateCompletedEvent()`와 동일하게 `CarePlanCommandService`의 private 메서드로 유지해, 기존 클래스 구조를 그대로 따르는 최소 변경으로 구현했다.

**테스트 중 발견하고 함께 수정한 부수 문제**: `CarePlanCompletedEventConsumeIntegrationTest`에 불일치 시나리오 테스트를 추가한 뒤, 같은 클래스의 기존 CANCELED 테스트가 간헐적으로 실패하는 현상을 발견했다. 원인은 불일치 이벤트가 `10.CarePlanCompleted이벤트소비.md`에서 구현한 Retry(최초 1회+재시도 3회, 총 약 7초) 대상이라, 불일치 테스트가 이 재시도가 끝나기 전에(1초만 대기하고) 먼저 종료해버리면 같은 컨슈머 스레드가 백그라운드에서 계속 이전 메시지를 재시도하는 동안 바로 다음 테스트의 메시지 처리가 지연되어 발생한 것이었다. 불일치 테스트가 DLQ(`care-plan.schedule-completed.dlq.queue`)에서 메시지를 직접 수신해 재시도가 완전히 소진될 때까지 기다리도록 고쳐 해결했고, `waitUntilCompleted()`의 폴링 예산도 2초 → 5초로 늘려 여유를 더 두었다. `CarePlanCompletedEventConsumeIntegrationTest`를 반복 재실행해 안정적으로 3/3 통과함을 확인했다.

**환경 관련 참고사항(10번 문서와 동일)**: 이 머신에 프로젝트 dev docker-compose 스택(`todak-*`)이 별도로 떠 있어, 여러 통합 테스트 클래스를 한꺼번에 묶어 실행하면 이번 변경과 무관한 `CarePlanCompletedEventRetryDlqIntegrationTest`(10번 구현분)에서 간헐적으로 `Connection refused`가 재현되었다. 이는 이미 이전 세션에서 사용자와 함께 확인한 동일한 Docker 리소스 경합 이슈이며, 이번 11번 범위의 테스트(`CarePlanCommandServiceTest`, `CarePlanCompletedEventConsumeIntegrationTest`)는 반복 실행 시 안정적으로 통과함을 확인했다.
