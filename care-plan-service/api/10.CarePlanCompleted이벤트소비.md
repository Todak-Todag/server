# 10. CarePlanCompleted 이벤트 소비 — Consumer Retry/DLQ 현황 분석

> 관련 이슈: [Feat] CarePlan 이벤트 발행·소비 안정성 및 정합성 개선 #283
> 이 문서는 **코드를 변경하지 않고** 현재 구조를 근거와 함께 분석한 기술 문서다.
> 참고: 이 문서에서 다루는 `CarePlanCompletedEvent`는 **schedule-service → care-plan-service**로 들어오는 인바운드 이벤트다. care-plan-service가 만들어 social-worker-service로 내보내는 `CarePlanCompletionEvent`(Outbox 적용됨, `09.CarePlanConfirmed이벤트발행.md` 4장 참고)와는 이름만 비슷할 뿐 별개다.

## 1. 현재 Consumer 처리 흐름

```
[schedule-service]
   rabbitTemplate.convertAndSend(SCHEDULE_EXCHANGE, SCHEDULE_COMPLETED_ROUTING_KEY, CarePlanCompletedEvent)
        │
        ▼
[RabbitMQ] schedule.exchange ──(schedule.completed.key)──▶ care-plan.schedule-completed.queue
        │
        ▼
CarePlanEventConsumer.consumeCarePlanCompleted()      [@RabbitListener(queues = CARE_PLAN_SCHEDULE_COMPLETED_QUEUE)]
   │
   ├─ log.info(수신 로그)
   ├─ CarePlanCommandService.completeCarePlan(event)   [@Transactional]
   │     ├─ validateCompletedEvent(event)
   │     │     - status == CANCELED → 통과
   │     │     - status != CANCELED && serviceResultId == null
   │     │           → BusinessException(CARE_PLAN_COMPLETED_EVENT_INVALID)
   │     ├─ serviceResultId != null 이면
   │     │     scheduleResultQueryPort.findById(serviceResultId)  ← schedule-service Feign 호출
   │     │           (ScheduleResultClientAdapter → ScheduleFeignClient
   │     │            → GET /internal/v1/service-results/{serviceResultId})
   │     ├─ carePlanCommandRepository.findById(carePlanId)
   │     │           .orElseThrow(() → BusinessException(CARE_PLAN_NOT_FOUND))
   │     ├─ carePlan.complete()
   │     │     - 현재 상태가 IN_PROGRESS가 아니면 false 반환, 아무 것도 하지 않고 종료(멱등 가드)
   │     │     - IN_PROGRESS면 COMPLETED로 전이 + true 반환
   │     └─ completed == true 이면 carePlanCompletionEventAppender.append(carePlan)
   │           → CarePlanOutboxEvent 저장 (같은 트랜잭션 안에서 커밋)
   └─ log.info(처리 완료 로그)
```

관련 파일:

- `careplan/infrastructure/messaging/CarePlanEventConsumer.java` — `@RabbitListener` 진입점
- `careplan/application/service/command/CarePlanCommandService.java` — `completeCarePlan()`, `validateCompletedEvent()`
- `careplan/application/port/ScheduleResultQueryPort.java`, `careplan/infrastructure/adapter/ScheduleResultClientAdapter.java`, `careplan/infrastructure/client/ScheduleFeignClient.java`
- `global/config/RabbitMqConfig.java` — `SCHEDULE_EXCHANGE`, `SCHEDULE_COMPLETED_ROUTING_KEY`, `CARE_PLAN_SCHEDULE_COMPLETED_QUEUE` (큐는 `new Queue(name, true)` — durable, DLX 바인딩 없음)

테스트 근거: `CarePlanCompletedEventConsumeIntegrationTest` — 성공 케이스(COMPLETED, CANCELED)만 존재하며, 예외 발생 시 재큐잉/DLQ 동작을 검증하는 테스트는 없다.

## 2. `BusinessException` / 시스템 예외 발생 시 현재 RabbitMQ 동작

`CarePlanEventConsumer.consumeCarePlanCompleted()`에는 `try/catch`가 전혀 없다. 즉 아래 경로에서 발생한 예외는 모두 리스너 메서드 밖으로 그대로 전파된다.

- `validateCompletedEvent()`의 `BusinessException(CARE_PLAN_COMPLETED_EVENT_INVALID)`
- `scheduleResultQueryPort.findById()`의 `FeignException`(schedule-service 404/5xx, 커넥션 타임아웃 등)
- `carePlanCommandRepository.findById()` 실패 시 `BusinessException(CARE_PLAN_NOT_FOUND)`
- 그 외 예기치 못한 `RuntimeException`(DB 커넥션 오류 등)

**중요:** `GlobalExceptionHandler`는 `@RestControllerAdvice`로, HTTP 요청(Controller) 계층에서만 동작한다. `@RabbitListener` 메서드에서 발생한 예외는 이 핸들러를 전혀 거치지 않는다 — Spring AMQP의 리스너 컨테이너(`SimpleMessageListenerContainer`)가 별도로 처리한다.

Spring AMQP 기본 동작(재시도 설정이 없을 때):

1. 리스너 메서드가 예외를 던지면 컨테이너가 이를 잡아 브로커에 `basic.nack`(또는 reject)을 보낸다.
2. 이때 재전달 여부는 `spring.rabbitmq.listener.simple.default-requeue-rejected`(기본값 `true`)를 따른다. care-plan-service는 이 값을 명시적으로 설정한 적이 없으므로 기본값 `true`가 그대로 적용된다.
3. `default-requeue-rejected = true` + 재시도 인터셉터(Retry Advice) 없음 ⇒ 메시지는 **즉시 같은 큐의 맨 앞으로 재전달**되고, 컨슈머는 곧바로 같은 메시지를 다시 처리한다.
4. 실패 원인(예: `CARE_PLAN_NOT_FOUND`처럼 재시도해도 절대 해결되지 않는 논리적 오류)이 그대로면 이 과정이 무한히 반복된다 — **poison message에 의한 무한 재큐잉 루프**.
5. 이 루프가 도는 동안 해당 컨슈머 스레드는 큐의 다른 메시지를 처리하지 못한다(head-of-line blocking). 또한 매 반복마다 `scheduleResultQueryPort.findById()` Feign 호출이 다시 실행되어 schedule-service에도 불필요한 부하가 반복적으로 발생한다.

이 문제는 이미 `docs/technical-debt/TECH_DEBT.md` 3번 항목("RabbitMQ 컨슈머 재시도/DLQ 정책 부재")에 동일하게 기록되어 있다. 이번 문서는 그 항목을 이슈 #283 범위에서 더 구체화한 것이다.

## 3. 현재 care-plan-service의 RabbitMQ Listener Retry 설정 존재 여부

**존재하지 않는다.** 아래 세 파일 어디에도 `spring.rabbitmq.listener.*` 키가 없다.

- `care-plan-service/src/main/resources/application.yml`
- `config-repo/care-plan-service-local.yml`
- `config-repo/care-plan-service-prod.yml`

## 4. `defaultRequeueRejected`와 현재 설정 기준 무한 재전달 가능성

2장에서 설명한 대로, 재시도 설정이 전혀 없는 상태에서 `default-requeue-rejected`의 기본값(`true`)이 그대로 적용되므로 **무한 재전달 가능성이 실제로 존재한다.** 재시도 횟수를 세는 장치(Spring Retry interceptor)가 없기 때문에 "몇 번 실패하면 멈춘다"는 상한 자체가 없다 — care-plan-service 쪽은 schedule-service처럼 3회라는 제한도 없는, 더 취약한 상태다.

예외적으로, 메시지 자체를 애플리케이션 예외가 아니라 **메시지 변환 단계**에서 실패시키는 경우(예: JSON을 `CarePlanCompletedEvent`로 역직렬화할 수 없는 손상된 메시지)는 Spring AMQP의 기본 에러 핸들러(`ConditionalRejectingErrorHandler`)가 이를 "치명적 예외"로 분류해 재큐잉 없이 즉시 폐기하는 경로를 타는 경우도 있다. 다만 이는 스키마가 명백히 깨진 메시지에 한정된 예외적 경로이며, `BusinessException`이나 `FeignException`처럼 **정상적으로 역직렬화는 되었지만 처리 중 실패하는 케이스**는 여전히 4번에서 설명한 무한 재큐잉 경로를 탄다.

## 5. `schedule-service`의 Retry 설정과 비교

`schedule-service`는 `config-repo/schedule-service-local.yml`, `config-repo/schedule-service-prod.yml`에 동일하게 아래 설정을 갖고 있다.

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        retry:
          enabled: true
          max-retries: 3
```

YAML 주석에도 "수신 재시도 — 3회, DLQ 미운용 / DLQ가 없으므로 3회 후 메시지는 폐기"라고 명시되어 있다. `schedule-service/global/config/RabbitMqConfig.java`의 `scheduleProviderMatchedQueue()` 주석("재시도 3회는 리스너 컨테이너 설정으로 처리")도 동일한 의도를 확인해준다.

| 항목 | care-plan-service (`CarePlanEventConsumer`) | schedule-service (`ProviderMatchedEventListener` 등) |
| --- | --- | --- |
| `spring.rabbitmq.listener.simple.retry` | 미설정 | `enabled: true`, `max-retries: 3` |
| 실패 시 동작 | 즉시 재큐잉, 무한 반복 가능 | 컨테이너 내부에서 최대 3회 재시도(브로커 재큐잉이 아닌 로컬 재시도) 후, DLQ가 없으므로 `RejectAndDontRequeueRecoverer`에 의해 메시지 폐기 |
| 실패 상한 | 없음 (무한 루프 위험) | 있음 (3회, 다만 폐기이므로 **유실** 위험) |
| DLQ | 없음 | 없음 |

즉 두 서비스 모두 DLQ는 없지만, 실패 시 결과가 다르다 — care-plan-service는 "무한 루프"로, schedule-service는 "3회 후 조용한 유실"로 실패 모드가 갈린다. 어느 쪽도 바람직하지 않으며, 이슈 #283은 care-plan-service에 **최소한 schedule-service 수준(상한 있는 재시도)**을 먼저 적용하고, DLQ 여부는 6장에서 별도로 검토하는 것으로 범위를 나눈다.

## 6. Retry 적용 시 예외 분류 제안

현재 `completeCarePlan()`에서 발생 가능한 예외를 재시도 유효성 기준으로 나누면 다음과 같다.

| 예외 | 성격 | 재시도 적합성 |
| --- | --- | --- |
| `BusinessException(CARE_PLAN_COMPLETED_EVENT_INVALID)` | payload 자체가 유효하지 않음(예: CANCELED가 아닌데 `serviceResultId`가 null) — 논리적 오류 | 재시도해도 결과가 바뀌지 않음 → **즉시 실패 처리 대상** |
| `BusinessException(CARE_PLAN_NOT_FOUND)` | 이벤트의 `carePlanId`가 DB에 없음 — 데이터 정합성 문제(메시지 순서 역전, 이미 삭제된 Care Plan 등) | 대부분 재시도로 해결되지 않지만, 드물게 트랜잭션 커밋 지연으로 인한 일시적 조회 실패일 수 있음 → 소수 회(1~2회) 재시도 후 실패 처리 |
| `FeignException`(schedule-service 응답 지연/5xx/커넥션 오류) | 외부 서비스의 일시적 장애 | **재시도 적합 대상** — 네트워크/가용성 문제는 시간이 지나면 해결될 가능성이 있음 |
| 그 외 `RuntimeException`(DB 커넥션 풀 고갈, 낙관적 락 충돌 등 인프라성 오류) | 일시적 인프라 문제일 가능성 높음 | **재시도 적합 대상** |

`BusinessException`처럼 "즉시 실패 처리"가 맞는 예외와 `FeignException`처럼 "재시도가 맞는" 예외를 구분하려면, Spring Retry의 `retryable-exceptions` / `stateless`(또는 `RetryOperationsInterceptor` 커스텀 구성)에서 예외 타입별로 다른 처리를 지정하는 방식을 검토할 수 있다. 현재 `spring.rabbitmq.listener.simple.retry`의 단순 `enabled`/`max-retries` 설정만으로는 예외 타입별 분기가 불가능하므로, 세밀한 분기가 필요하다면 `RetryInterceptorBuilder`를 이용한 커스텀 `RetryOperationsInterceptor` Bean 등록이 필요하다는 점도 함께 기록해 둔다(현재 코드베이스 어디에도 이런 커스텀 Bean은 없다).

## 7. DLQ를 적용할 경우 필요한 Exchange / Queue / Routing Key 변경사항

현재 `RabbitMqConfig`(care-plan-service)의 관련 Bean:

```java
public static final String SCHEDULE_EXCHANGE = "schedule.exchange";
public static final String SCHEDULE_COMPLETED_ROUTING_KEY = "schedule.completed.key";
public static final String CARE_PLAN_SCHEDULE_COMPLETED_QUEUE = "care-plan.schedule-completed.queue";

@Bean
public Queue carePlanScheduleCompletedQueue() {
    return new Queue(CARE_PLAN_SCHEDULE_COMPLETED_QUEUE, true);
}
```

DLQ를 도입하려면 최소한 아래가 추가되어야 한다(현재 코드에는 전혀 없음).

- **DLX(Dead Letter Exchange)** — 예: `care-plan.dlx.exchange`라는 새 `DirectExchange` Bean
- **DLQ(Dead Letter Queue)** — 예: `care-plan.schedule-completed.dlq`라는 새 `Queue` Bean과 DLX에 대한 바인딩
- **원본 큐(`carePlanScheduleCompletedQueue`)에 DLX 지정** — `Queue` 생성 시 `x-dead-letter-exchange`, (필요 시) `x-dead-letter-routing-key` 인자를 추가해야 한다. 현재 `new Queue(CARE_PLAN_SCHEDULE_COMPLETED_QUEUE, true)`는 이런 arguments 없이 생성되므로, `QueueBuilder.durable(...).withArgument("x-dead-letter-exchange", ...)` 형태로 재정의해야 한다.
- **재시도 소진 후 라우팅 방식** — Spring Retry의 기본 `Recoverer`는 `RejectAndDontRequeueRecoverer`로, 재시도를 다 쓴 메시지를 `requeue=false`로 reject한다. 큐에 DLX가 걸려 있으면 이 reject된 메시지가 자동으로 DLX→DLQ로 이동한다. 별도의 커스텀 `MessageRecoverer`(예: `RepublishMessageRecoverer`)를 등록하면 실패 사유(exception 메시지, 스택 트레이스 등)를 헤더에 남겨 DLQ 메시지에 포함시킬 수도 있다 — 현재는 어떤 Recoverer도 등록되어 있지 않다.

## 8. DLQ를 적용하지 않을 경우 가능한 최종 실패 처리 방식

DLQ 인프라(Exchange/Queue 추가, 운영 모니터링 대상 확대)를 당장 도입하지 않는다면, 최소한 아래 중 하나는 필요하다.

- **재시도 소진 후 로그만 남기고 메시지 폐기(현재 schedule-service와 동일한 방식)** — `spring.rabbitmq.listener.simple.retry`만 적용하고 DLQ는 붙이지 않는 방식. 구현이 가장 간단하지만, 실패한 이벤트를 사후에 재처리할 방법이 전혀 없다는 한계가 그대로 남는다(schedule-service도 동일한 한계를 이미 안고 있음).
- **최종 실패 시 별도 실패 기록을 남기는 리커버러 등록** — `MethodInvocationRecoverer` 또는 커스텀 에러 핸들러에서 최종 실패 시 `carePlanId`, `serviceResultId`, 실패 사유를 ERROR 레벨 로그로 구조화해 남긴다. 별도 테이블 적재까지는 이번 이슈 범위를 벗어나는 선택이 될 수 있다.

두 방식 모두 "코드 구현이 필요한 부분"이며, 어느 쪽을 선택할지는 운영팀의 장애 대응 여력과 결부된 판단이므로 이 문서에서 결론을 내리지 않고 검토안으로 남긴다.

## 9. 예상 수정 파일 목록

- `global/config/RabbitMqConfig.java` — DLX/DLQ 적용 시 Exchange/Queue/Binding 추가, 원본 큐에 dead-letter 인자 추가
- `src/main/resources/application.yml`, `config-repo/care-plan-service-local.yml`, `config-repo/care-plan-service-prod.yml` — `spring.rabbitmq.listener.simple.retry.*` 추가
- `careplan/infrastructure/messaging/CarePlanEventConsumer.java` — 예외 분류(즉시 실패 vs 재시도)를 코드 레벨에서 구분해야 한다면 예외 래핑/재던지기 로직 추가 검토
- (커스텀 재시도 인터셉터가 필요할 경우) `global/config/RabbitMqConfig.java` 또는 신규 설정 클래스에 `RetryOperationsInterceptor` Bean 추가
- `global/exception/ErrorCode.java` — 최종 실패 처리 방식에 따라 신규 에러 코드가 필요할 수 있음

## 10. 테스트해야 할 시나리오

- `BusinessException(CARE_PLAN_COMPLETED_EVENT_INVALID)` 발생 시 재시도 여부(재시도 대상에서 제외되어야 한다면 즉시 실패 처리되는지)
- `BusinessException(CARE_PLAN_NOT_FOUND)` 발생 시 설정된 횟수만큼만 재시도되고 이후 최종 실패 처리(로그 또는 DLQ)로 이어지는지
- `FeignException`(schedule-service 응답 실패 모사) 발생 시 설정된 `max-retries`만큼 재시도된 뒤 최종 실패 처리로 이어지는지
- 재시도 소진 후 DLQ를 적용한 경우, 메시지가 실제로 DLQ 큐에 도착하는지, 원본 큐에는 더 이상 남아있지 않은지
- DLQ를 적용하지 않은 경우, 재시도 소진 후 메시지가 더 이상 무한 재큐잉되지 않고(원본 큐가 비워짐) 실패 로그가 남는지
- 정상 케이스(`CarePlanCompletedEventConsumeIntegrationTest`에 이미 있는 COMPLETED/CANCELED 성공 시나리오)가 재시도 설정 도입 후에도 여전히 1회 만에 성공 처리되는지(불필요한 재시도가 발생하지 않는지) 회귀 검증
