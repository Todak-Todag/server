> 관련 이슈: [Feat] CarePlan 이벤트 발행·소비 안정성 및 정합성 개선 #283
>
> **문서 상태: 구현 완료 (2026-09-13).** 1~7장은 Outbox 전환 전 현황을 분석한 원본 내용을 그대로 남겨 두었고(과거 문제 상황을 이해하는 데 필요), 8장부터 실제 구현 결과·문서와 달라진 부분을 반영했다. 코드가 우선이며, 아래 실제 구현 내용과 이전 분석이 다른 경우 실제 코드가 맞다.

## 1. 현재 흐름 — 호출 체인

`CarePlanConfirmed` 이벤트는 Care Plan 상태가 `CONFIRMED`로 바뀔 때 다음 호출 체인을 거쳐 발행된다.

```
PATCH /api/v1/care-plans/{carePlanId}/status
  └─ CarePlanController.updateCarePlanStatus()
       └─ CarePlanCommandService.updateCarePlanStatus()          [@Transactional]
            ├─ carePlan.canTransitionTo(CONFIRMED) 검증 (CarePlan.java)
            ├─ carePlan.updateStatus(CONFIRMED)                   ← DB 반영 (커밋 전, 영속성 컨텍스트 内)
            ├─ userQueryPort.findById(patientId)                 ← user-service Feign 호출 (트랜잭션 내부)
            ├─ createCarePlanConfirmedEvent(...)                 ← 이벤트 payload 조립
            └─ applicationEventPublisher.publishEvent(carePlanConfirmedEvent)
                                                                   ← Spring ApplicationEvent 발행 (아직 RabbitMQ 아님)
       (메서드 정상 종료 → @Transactional AOP가 트랜잭션 커밋)
            └─ 커밋 완료 시점에 TransactionSynchronizationManager가
                 AFTER_COMMIT 콜백 실행
                      └─ CarePlanConfirmedEventListener.handle()   [@TransactionalEventListener(AFTER_COMMIT)]
                           └─ carePlanEventPort.publishCarePlanConfirmed()
                                └─ CarePlanEventPublisher (RabbitMQ 발행 어댑터)
                                     └─ rabbitTemplate.convertAndSend(
                                            RabbitMqConfig.CARE_PLAN_CONFIRMED_EXCHANGE,
                                            RabbitMqConfig.CARE_PLAN_CONFIRMED_ROUTING_KEY,
                                            carePlanConfirmedEvent)
```

관련 파일:

- `careplan/application/service/command/CarePlanCommandService.java` — `updateCarePlanStatus()`, `createCarePlanConfirmedEvent()`, `createConfirmedServices()`
- `careplan/application/event/CarePlanConfirmedEvent.java` — 이벤트 payload record (`carePlanId`, `regionId`, `services[].{planServiceId, provideServiceId, preferences[]}`)
- `careplan/infrastructure/messaging/CarePlanConfirmedEventListener.java` — `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`
- `careplan/application/port/CarePlanEventPort.java` — `publishCarePlanConfirmed(CarePlanConfirmedEvent)`
- `careplan/infrastructure/messaging/CarePlanEventPublisher.java` — `CarePlanEventPort` 구현체, `RabbitTemplate.convertAndSend()` 직접 호출
- `global/config/RabbitMqConfig.java` — `CARE_PLAN_CONFIRMED_EXCHANGE = "care-plan.exchange"`, `CARE_PLAN_CONFIRMED_ROUTING_KEY = "care-plan.confirmed.key"`

테스트 근거: `CarePlanConfirmedEventPublishIntegrationTest.carePlanConfirmedEventPublish_success()` — `updateCarePlanStatus()` 호출 후 실제 RabbitMQ 큐에서 메시지를 `receive()`하여 payload를 검증하고 있어, 위 호출 체인이 실제로 이렇게 동작함을 확인할 수 있다.

## 3. RabbitMQ 장애 시 이벤트가 유실되는 이유

핵심 원인은 **"DB 상태 변경"과 "이벤트 발행"이 서로 다른 저장소에 있고, 이벤트 쪽에는 영속성이 전혀 없다**는 것이다.

- `CarePlanEventPublisher.publishCarePlanConfirmed()`는 `rabbitTemplate.convertAndSend(...)`를 **단 한 번** 호출하고 끝난다. 재시도 로직, 실패 기록, 별도 저장소 어디에도 없다.
- `RabbitMqConfig`에는 `publisher-confirm-type` / `publisher-returns` 관련 설정이 없다 (`application.yml`, `care-plan-service-local.yml`, `care-plan-service-prod.yml` 어디에도 `spring.rabbitmq.publisher-confirm-type` 키가 없음). 따라서 `convertAndSend()`가 예외 없이 반환되었다고 해서 브로커가 실제로 메시지를 받았다는 보장이 없다 — 커넥션이 살아있는 동안의 라우팅 실패(예: 존재하지 않는 Exchange)나 네트워크 순단은 애플리케이션이 감지할 방법이 없다.
- 만약 `convertAndSend()`가 예외를 던지는 경우(예: 브로커 연결 자체가 끊어진 경우)라면, 이 호출은 `CarePlanConfirmedEventListener.handle()` — 즉 `AFTER_COMMIT` 콜백 — 내부에서 실행된다. `AFTER_COMMIT` 콜백은 **트랜잭션이 이미 커밋된 뒤** 같은 스레드에서 동기적으로 실행되므로, 예외가 발생해도 되돌릴 DB 상태가 없다. 즉:
  1. `CarePlan.status`는 이미 `CONFIRMED`로 영구 반영됨.
  2. `CarePlanConfirmedEvent`는 메모리상의 Java 객체로만 존재했다가, 발행 실패와 동시에 완전히 사라짐. 재구성할 수 있는 원천 데이터(어떤 Care Plan이 언제 CONFIRMED 되었는지)는 DB의 `status` 컬럼 하나뿐이며, 이것만으로는 "이벤트를 다시 만들어 보내야 한다"는 사실 자체를 감지할 수 없다.
  3. `CarePlan.canTransitionTo()` (`CarePlan.java`)를 보면 `CONFIRMED` 상태에서 허용되는 다음 전이는 `IN_PROGRESS`뿐이다. 즉 클라이언트가 실패를 감지하고 `CONFIRMED` 요청을 재시도해도, 이미 `CONFIRMED`인 Care Plan은 `canTransitionTo(CONFIRMED)`가 `false`를 반환해 `CARE_PLAN_INVALID_STATUS_TRANSITION` 예외로 거부된다. **재시도로 복구할 방법 자체가 없다.**
- 정리하면, 이 이벤트가 유실되면 Care Plan은 `CONFIRMED`로 남지만 이벤트를 구독하는 다른 서비스(예: provider-service의 매칭 프로세스)는 이 사실을 영원히 알 수 없다. 원인 추적 근거도 로그(있다면)뿐이며, 현재 `CarePlanEventPublisher`에는 발행 성공/실패 로그조차 없다.

## 4. `CarePlanCompleted` Outbox 구조와의 비교

같은 서비스 안에 이미 Outbox 패턴이 구현되어 있는 이벤트가 있다 — `CarePlanCompletionEvent`(care-plan-service → social-worker-service, "Care Plan 완료" 알림). 이 이벤트는 스케줄 완료 이벤트를 **수신**한 뒤 파생되어 나가는 별개의 아웃바운드 이벤트로, `CarePlanCompletedEvent`(schedule-service → care-plan-service, 인바운드)와 이름이 유사하지만 다른 개념이다. 혼동 방지를 위해 아래 표에서는 코드상의 클래스명을 그대로 사용한다.

| 구분 | `CarePlanConfirmedEvent` (현재) | `CarePlanCompletionEvent` (Outbox 적용됨) |
| --- | --- | --- |
| DB 반영과 이벤트 발행의 원자성 | 없음 — DB 커밋과 RabbitMQ 발행이 별개 작업 | 있음 — `CarePlanCompletionEventAppender.append()`가 상태 변경과 같은 `@Transactional` 안에서 Outbox 테이블에 INSERT (`CarePlanCommandService.completeCarePlan()` 참고) |
| 이벤트 발행 트리거 | Spring `ApplicationEventPublisher` + `@TransactionalEventListener(AFTER_COMMIT)` | `@Scheduled` 폴링 스케줄러(`CarePlanOutboxRelayScheduler`, `fixedDelayString = 5000ms`)가 `PENDING` 상태 이벤트를 주기적으로 조회 후 발행 |
| 발행 실패 시 재시도 | 없음 (1회성 호출) | 있음 — `CarePlanOutboxCommandService.recordFailure()`가 `retryCount` 증가, 다음 폴링 주기에 재시도 |
| 3회 실패 후 처리 | 해당 없음(재시도 자체가 없으므로) | `CarePlanOutboxEvent.recordFailure()`에서 `retryCount >= MAX_RETRY_COUNT(3)`이면 `FAILED`로 전환 |
| 발행 성공 기록 | 없음 | `CarePlanOutboxCommandService.markSent()` → `SENT` + `publishedAt` 기록 |
| RabbitMQ로 실제 전송하는 클래스 | `CarePlanEventPublisher` (호출 주체: `@TransactionalEventListener`) | `CarePlanCompletedEventRabbitAdapter` (호출 주체: `CarePlanOutboxRelayFacade`) |
| 브로커 장애 시 결과 | 이벤트 영구 유실 (위 3장 참고) | Outbox에 `PENDING`으로 남아 다음 폴링에서 재시도 — 유실 아님 |

## 5. 재사용 가능한 기존 Outbox 인프라

Confirmed 이벤트를 Outbox로 옮길 때, 아래 클래스들은 **이미 존재하며 구조적으로 재사용 가능**하다 (단, 5장·6장에서 설명하는 수준의 일반화는 필요하다).

| 계층 | 클래스 | 현재 역할 |
| --- | --- | --- |
| Entity | `careplan/domain/entity/CarePlanOutboxEvent.java` | `id`, `aggregateId`, `payload`(TEXT), `status`, `retryCount`, `lastErrorMessage`, `publishedAt` 보유. `create()`, `markSent()`, `recordFailure()` |
| Entity | `careplan/domain/entity/CarePlanOutboxEventStatus.java` | `PENDING`, `SENT`, `FAILED` |
| Repository(Command) | `CarePlanOutboxEventCommandRepository` / `CarePlanOutboxEventCommandRepositoryImpl` | `save()`, `findById()` |
| Repository(Query) | `CarePlanOutboxEventQueryRepository` / `CarePlanOutboxEventQueryRepositoryImpl` | `findByStatus(status, limit)` → `SpringDataCarePlanOutboxEventRepository.findByStatusOrderByCreatedAtAsc()` |
| Application Service | `CarePlanOutboxCommandService` | `markSent(outboxEventId)`, `recordFailure(outboxEventId, errorMessage)` — 상태 전이 전담 |
| Application Service | `CarePlanOutboxQueryService` | `findPending(batchSize)` |
| Scheduler | `CarePlanOutboxRelayScheduler` | `@ConditionalOnProperty("care-plan.outbox.relay.enabled")`, `@Scheduled(fixedDelayString = "${care-plan.outbox.relay.fixed-delay-ms:5000}")` |
| Facade | `CarePlanOutboxRelayFacade` | `relay()` → `findPending()` 순회 → 역직렬화 → 발행 → `markSent`/`recordFailure` |

이 인프라의 **테이블 구조(`p_care_plan_outbox_events`, `aggregateId`+`payload` TEXT)와 상태 전이(`PENDING`/`SENT`/`FAILED`) 자체는 특정 이벤트 타입에 종속되지 않는다.** 문제는 아래 6장에서 보듯 리포지토리 상위 계층(직렬화기, Relay, 발행 어댑터)이 `CarePlanCompletionEvent` 하나만 알도록 하드코딩되어 있다는 점이다.

## 6. Confirmed 이벤트를 Outbox에 넣기 위해 변경해야 하는 클래스

현재 Outbox 관련 클래스들은 **이벤트 타입이 하나(`CarePlanCompletionEvent`)라는 전제**로 짜여 있다. Confirmed를 같은 테이블에 함께 태우려면 아래가 모두 바뀌어야 한다.

1. **`CarePlanCompletionEventPayloadSerializer`** — 현재 `serialize(CarePlanCompletionEvent)` / `deserialize(String) → CarePlanCompletionEvent`로 타입이 고정되어 있다. Confirmed 이벤트도 Outbox에 넣으려면 이 타입 고정을 풀어야 한다(범용 `ObjectMapper` 기반 직렬화/역직렬화로 일반화하거나, 이벤트 타입별 역직렬화 대상 클래스를 알아야 함).
2. **`CarePlanCompletionEventAppender`** — `CarePlanCompletionEvent`를 직접 생성해 Outbox에 저장한다. Confirmed용으로 별도 Appender를 만들거나, 이 클래스를 이벤트 타입을 인자로 받는 형태로 일반화해야 한다.
3. **`CarePlanOutboxRelayFacade.relayOne()`** — 지금은 `carePlanCompletionEventPayloadSerializer.deserialize(...)`로 **무조건 `CarePlanCompletionEvent`로만** 역직렬화한 뒤 `carePlanCompletedEventPort.publish(event)` **한 곳으로만** 보낸다. Confirmed 이벤트가 같은 테이블에 섞이면, 조회된 row가 어떤 이벤트 타입인지 구분할 방법이 현재 스키마(`aggregateId`, `payload`뿐)에는 없다 → 7장의 `eventType` 도입이 사실상 선행 조건이다.
4. **`CarePlanCompletedEventPort` / `CarePlanCompletedEventRabbitAdapter`** — 이름과 구현 모두 `CarePlanCompletionEvent` 전용으로 고정되어 있다(`CARE_PLAN_COMPLETED_EXCHANGE`/`CARE_PLAN_COMPLETED_ROUTING_KEY`만 사용). Confirmed는 다른 Exchange/Routing Key(`CARE_PLAN_CONFIRMED_EXCHANGE`/`CARE_PLAN_CONFIRMED_ROUTING_KEY`)로 나가야 하므로, 이 Port/Adapter를 이벤트 타입별로 분기하거나 여러 개로 나눠야 한다.
5. **`CarePlanCommandService.updateCarePlanStatus()`** — 현재 `applicationEventPublisher.publishEvent(carePlanConfirmedEvent)`를 호출하는 부분을, `CarePlanCompletionEventAppender.append(carePlan)`과 동일한 패턴으로 Outbox INSERT를 호출하도록 바꿔야 한다.
6. **`CarePlanConfirmedEventListener` / `CarePlanEventPublisher` / `CarePlanEventPort`** — Outbox 경유로 전환되면 이 세 클래스(AFTER_COMMIT 리스너, 즉시발행 어댑터, 그 포트)는 더 이상 필요하지 않아 제거 대상이 된다. (다만 이번 단계는 문서 작성까지이므로 실제 제거는 하지 않는다.)

## 7. `eventType` 도입 시 영향받는 코드

이슈 #283의 2·3번 항목(Confirmed/Completed가 같은 Outbox 테이블을 공유하고 `eventType`으로 구분)을 적용하면 아래가 영향을 받는다.

- **`CarePlanOutboxEvent`(Entity)** — 현재 컬럼은 `outbox_event_id`, `aggregate_id`, `payload`, `status`, `retry_count`, `last_error_message`, `published_at`뿐이며 `eventType`에 해당하는 컬럼이 없다. 엔티티에 필드 추가 + `create()` 정적 팩토리 메서드 시그니처 변경이 필요하다.
- **DB 스키마** — `p_care_plan_outbox_events` 테이블(`ddl-auto: update`인 local 환경은 자동 반영되지만, prod는 `ddl-auto: validate`이므로 실제 마이그레이션 DDL이 별도로 필요하다 — `schedule-service-prod.yml`의 `p_schedule_outbox_events` 관련 TODO 주석과 동일한 패턴).
- **`CarePlanOutboxEventResult`** — `outboxEventId`, `aggregateId`, `payload`만 담고 있어 `eventType`을 Relay까지 전달하려면 필드 추가가 필요하다.
- **`CarePlanCompletionEventAppender` / (신설될) Confirmed용 Appender** — Outbox row 생성 시 자신의 이벤트 타입 값을 함께 저장해야 한다.
- **`CarePlanOutboxRelayFacade.relayOne()`** — `pendingEvent.eventType()` 값에 따라 역직렬화 대상 클래스, 발행 Port(Exchange/Routing Key)를 분기해야 한다 (8번 항목과 연결).
- **`CarePlanOutboxQueryService.findPending()` / `CarePlanOutboxEventQueryRepository.findByStatus()`** — 현재는 상태(`PENDING`)만으로 조회한다. 이벤트 타입과 무관하게 배치 처리하는 지금 구조를 유지할지, 타입별로 나눠 조회할지는 Relay의 분기 방식 설계에 따라 결정해야 한다.

- `careplan/application/event/CarePlanConfirmedEventPayloadSerializer.java` — `CarePlanCompletionEventPayloadSerializer`와 동일한 형태로 Confirmed 전용 직렬화기 신설 (일반화하지 않고 병행 클래스로 결정 — 11장 참고)

- `careplan/domain/entity/CarePlanOutboxEvent.java` — `eventType` 필드 추가(`@Enumerated(STRING)` + `@JdbcTypeCode(NAMED_ENUM)`, 컬럼 `event_type`), `create()` 팩토리 시그니처에 `eventType` 파라미터 추가

## 10. 변경 후 흐름 (텍스트 다이어그램, 실제 구현 결과)

```
CarePlanCommandService.updateCarePlanStatus()  ── @Transactional
   │
   ├─ CarePlan.status = CONFIRMED
   ├─ createCarePlanConfirmedEvent(...)  ── 기존 조립 로직 그대로 유지
   └─ CarePlanConfirmedEventAppender.append(event)
        ├─ CarePlanConfirmedEventPayloadSerializer.serialize(event)
        └─ CarePlanOutboxEvent.create(event.carePlanId(), CARE_PLAN_CONFIRMED, payload)
             └─ CarePlanOutboxEventCommandRepository.save(...)
   ▼
[트랜잭션 커밋]  ── 상태 변경 + Outbox INSERT가 원자적으로 커밋 (Completed와 동일 보장)
   │
   ▼ (최대 5초 이내, 폴링 주기)
CarePlanOutboxRelayScheduler → CarePlanOutboxRelayFacade.relay() → relayOne() → publish()
   │
   ├─ findPending(batchSize) 조회
   ├─ eventType == CARE_PLAN_CONFIRMED
   │     → CarePlanConfirmedEventPayloadSerializer.deserialize() → CarePlanConfirmedEventPort.publish()
   │       (CarePlanConfirmedEventRabbitAdapter → CARE_PLAN_CONFIRMED_EXCHANGE / CARE_PLAN_CONFIRMED_ROUTING_KEY)
   └─ eventType == CARE_PLAN_COMPLETED
         → CarePlanCompletionEventPayloadSerializer.deserialize() → CarePlanCompletedEventPort.publish()
           (CarePlanCompletedEventRabbitAdapter → CARE_PLAN_COMPLETED_EXCHANGE / CARE_PLAN_COMPLETED_ROUTING_KEY, 무변경)
        │
        ├─ 성공 → markSent()
        └─ 실패 → recordFailure() (3회 후 FAILED, 다음 폴링에서 재시도 제외)
```

브로커 장애가 발생해도 Outbox row는 `PENDING`으로 DB에 남아 있으므로, Confirmed 이벤트도 Completed와 동일하게 **다음 폴링 주기에 자동 재시도**된다 — 3장에서 설명한 "재시도 불가능한 영구 유실" 문제가 구조적으로 해소되었다.

## 11. 문서와 실제 구현이 갈렸던 결정 사항

구현 착수 전 사용자에게 직접 확인한 설계 결정 하나를 기록한다.

**`CarePlanConfirmedEventAppender`가 이벤트를 스스로 조립할지, 완성된 이벤트를 받아 저장만 할지** — 두 가지 선택지가 있었다.

- A안(채택): Thin Appender. 이벤트 조립(`createCarePlanConfirmedEvent()`, `createConfirmedServices()`)은 `CarePlanCommandService`에 그대로 두고, `CarePlanConfirmedEventAppender`는 완성된 `CarePlanConfirmedEvent`를 받아 직렬화+Outbox 저장만 수행.
- B안(미채택): Smart Appender. `CarePlanCompletionEventAppender`(`CarePlan` 엔티티를 받아 스스로 조립)와 완전히 동일한 모양으로, Confirmed용 조회 리포지토리 의존성까지 Appender로 이관.

**A안을 채택한 이유**: 이번 작업의 핵심은 발행 경로를 Outbox로 바꾸는 것이지 이벤트 조립 책임을 재배치하는 것이 아니며, 이미 테스트로 검증된 조립 로직을 옮기지 않아 회귀 위험이 가장 낮기 때문이다. 그 결과 `CarePlanConfirmedEventAppender`와 `CarePlanCompletionEventAppender`는 책임 범위가 비대칭적이다(전자는 완성된 이벤트를 받고, 후자는 엔티티를 받아 스스로 조립) — 이는 의도된 트레이드오프이며 향후 세 번째 이벤트 타입이 추가될 때 재검토할 만한 지점이다.

그 외 5~8장에서 예상했던 내용(재사용 가능한 Outbox 인프라, `eventType` 영향 범위, Confirmed 전용 클래스 신설)은 실제 구현과 방향이 일치했다. 유일하게 사전에 알 수 없었던 부분은 DB 스키마였는데, 착수 시점에 이미 `docker/postgres/care-plan-service.sql`에 `event_type` 컬럼/enum이 준비되어 있어 별도 마이그레이션 설계 없이 그대로 사용했다(8장 DB 항목 참고).
