## 1. 현재 Outbox 상태값과 상태 전이

```java
// careplan/domain/entity/CarePlanOutboxEventStatus.java
public enum CarePlanOutboxEventStatus {
    PENDING,
    SENT,
    FAILED
}
```

전이는 `CarePlanOutboxEvent`(Entity) 내부 메서드로만 이루어진다.

- `create(aggregateId, payload)` → `status = PENDING`, `retryCount = 0`
- `markSent()` → `status = SENT`, `publishedAt = Instant.now()`
- `recordFailure(errorMessage)` → `retryCount++`, `lastErrorMessage = errorMessage`; `retryCount >= MAX_RETRY_COUNT(3)`
  이면 `status = FAILED`, 아니면 `status`는 그대로 `PENDING` 유지

### `PENDING → SENT`

`CarePlanOutboxRelayFacade.relayOne()`이 `carePlanCompletedEventPort.publish(event)` 호출에 성공하면
`CarePlanOutboxCommandService.markSent(pendingEvent.outboxEventId())`를 호출한다.

### 실패 시 `retryCount` 증가 흐름

`relayOne()`의 `catch (Exception e)` 블록에서
`carePlanOutboxCommandService.recordFailure(pendingEvent.outboxEventId(), e.getMessage())`를 호출한다. 이때 상태는 여전히 `PENDING`으로
남아 있으므로, 다음 폴링 주기(`CarePlanOutboxRelayScheduler`, 기본 5초)에 `CarePlanOutboxQueryService.findPending()`이 다시 이 row를 조회해
재시도한다.

### 3회 실패 후 `FAILED`가 되는 흐름

`CarePlanOutboxEvent.recordFailure()` 내부에서 `retryCount >= MAX_RETRY_COUNT`(3) 체크가 이루어지며, 3번째 실패 시점에 `status = FAILED`로
전환된다. `CarePlanOutboxCommandService.recordFailure()`는 이 상태가 `FAILED`가 되면 `log.error(...)`로 최종 실패를 별도 로그로 남긴다.

## 2. `FAILED` 이후 현재 이루어지는 처리

**아무 처리도 없다.** `CarePlanOutboxQueryService.findPending()`은
`CarePlanOutboxEventQueryRepository.findByStatus(CarePlanOutboxEventStatus.PENDING, batchSize)`만 호출한다 — 즉 `FAILED` 상태는
스케줄러의 조회 대상에서 아예 제외된다. `FAILED`로 전환된 이벤트를 다시 `PENDING`으로 되돌리거나 재발행을 트리거하는 코드, API, 배치는 코드베이스 어디에도 없다. 사실상 `FAILED` row는
DB에 영구히 남아있을 뿐 그 이후로는 방치된다.

## 3. 운영자가 `FAILED` 이벤트를 확인할 수 있는 현재 수단

`CarePlanOutboxCommandService.recordFailure()` 내부의
`log.error("[CarePlan] Outbox 이벤트 최종 발행 실패 outboxEventId={} retryCount={}", ...)`가 **유일한 신호**다. 이 외에는:

- Actuator/Micrometer 관련 커스텀 메트릭 — 없음. `build.gradle`에 `spring-boot-starter-actuator`와 `micrometer-registry-prometheus`가
  의존성으로는 포함되어 있으나(런타임 전용), 코드베이스 전체를 검색해도 `MeterRegistry`, `Counter`, `Gauge`를 사용하는 코드는 한 곳도 없다. 즉 기본 제공되는 JVM/HTTP 지표
  외에 "Outbox FAILED 건수" 같은 도메인 지표는 노출되지 않는다.
- Grafana 대시보드 — 프로젝트 내에 관련 설정/대시보드 정의 파일 없음.
- 관리자 API — `CarePlanInternalController`(`/internal/v1/...`)를 포함해 Outbox 이벤트를 조회/재처리하는 어떤 엔드포인트도 존재하지 않는다.

즉 현재는 **로그를 직접 검색(예: `grep`, 로그 수집기 쿼리)하는 것 외에는 운영자가 `FAILED` 이벤트의 존재를 알 방법이 없다.**

## 4. 로그 / Actuator Metric / Grafana Metric / 관리자 API 비교

| 방식                          | 구현 비용     | 현재 프로젝트에서의 준비 상태                                                               | 장점                                           | 단점                                                            |
|-----------------------------|-----------|--------------------------------------------------------------------------------|----------------------------------------------|---------------------------------------------------------------|
| 로그(현재 상태)                   | 없음(이미 있음) | 이미 구현됨(`log.error`)                                                            | 추가 비용 0                                      | 능동적으로 찾아봐야 함, 알림 체계 없이는 장애 인지가 늦어짐                            |
| Actuator Custom Metric      | 낮음        | `actuator`/`micrometer-registry-prometheus` 의존성은 이미 있음(연동 인프라만 있고 커스텀 지표는 미구현) | `FAILED` 건수를 Gauge로 노출해 기존 모니터링 스택에 바로 연동 가능 | Prometheus를 실제로 스크레이핑하는 운영 인프라가 갖춰져 있어야 의미가 있음(현재 이 저장소 범위 밖) |
| Grafana Dashboard           | 중간        | 없음 — Prometheus 연동과 대시보드 정의가 모두 선행되어야 함                                        | 시각화, 추세 파악에 유리                               | 이번 프로젝트 규모/단계 대비 구축 비용이 큼                                     |
| 관리자 API(FAILED 조회 + 수동 재발행) | 중간        | 없음 — 신규 엔드포인트/서비스 로직 필요                                                        | 운영자가 직접 확인하고 즉시 조치(재처리) 가능                   | 엔드포인트 인증/권한 설계, 재처리 시 중복 발행 방지 등 추가 설계 필요                     |

**현재 프로젝트 규모에 적합한 방식:** 이미 있는 `spring-boot-starter-actuator` + `micrometer-registry-prometheus` 의존성을 활용해 `FAILED` 건수를
노출하는 커스텀 Gauge/Counter를 추가하는 것이 비용 대비 효과가 가장 크다(신규 의존성 도입이 필요 없고, 기존 인프라를 그대로 재사용). Grafana 대시보드는 Prometheus 스크레이핑 인프라가
실제로 운영되고 있다는 전제가 있어야 의미가 있으므로, 그 전제가 이 저장소 범위에서 확인되지 않는 한 우선순위가 낮다. 관리자 API(수동 재처리)는 "탐지"가 아니라 "조치" 수단이므로 5번 항목에서 별도로
다룬다.

## 5. 수동 재처리 구현 필요성

**필요하다고 판단할 근거가 있다.** 현재 `FAILED` 상태가 된 이벤트를 되살릴 방법이 전혀 없다(2번 항목 참고). 만약 실제 운영 환경에서 RabbitMQ 브로커가 짧게라도 3회의 폴링 주기(기본 5초
간격이므로 약 15초 이상) 이상 응답하지 못하면, 그 사이에 처리 대상이었던 이벤트는 영구히 `FAILED`로 굳어지고 이후 브로커가 정상화되어도 자동으로는 재발행되지 않는다. 최소한 다음 중 하나는 필요하다.

- `FAILED → PENDING`으로 되돌리는 관리자 API(단건 또는 벌크) — 재조회 스케줄러가 그 이후 자동으로 재시도하도록
- 혹은 동일한 효과를 내는 배치/스크립트(운영자가 수동 실행)

이번 이슈(#283)의 "5. Outbox `FAILED` 이벤트의 운영 확인 및 재처리 방안 검토" 항목은 (이 문서 작성 시점 기준) **구현 여부까지 이번 단계에서 결정하기보다, 최소 하나의 구현 방식(관리자 API 또는 배치)이
필요하다는 점을 확인하는 선에서 정리**했다. → 실제로는 이후 **10장에서 "FAILED 목록 조회 + 재처리 API"로 구현**되었다.

## 6. 현재 단일 인스턴스에서 Outbox Relay 동시성 문제 발생 여부

**발생하지 않는다.** 근거:

- `CarePlanOutboxRelayScheduler.relay()`는
  `@Scheduled(fixedDelayString = "${care-plan.outbox.relay.fixed-delay-ms:5000}")`로 등록되어 있다. `fixedDelay`는 **이전 실행이 끝난
  시점부터** 지정된 시간만큼 대기 후 다음 실행을 시작하는 방식이므로, 같은 인스턴스 안에서 두 번의 `relay()` 실행이 동시에 겹치는 일이 없다(스케줄러 클래스의 Javadoc 주석에도 이 의도가 명시되어
  있다).
- 별도의 비동기 트리거(이벤트 기반 즉시 발행 등)도 없고, `CarePlanOutboxRelayFacade.relay()`를 호출하는 진입점이 이 스케줄러 하나뿐이다.

따라서 단일 인스턴스 환경에서는 같은 Outbox row를 두 스레드가 동시에 조회·발행할 가능성 자체가 없다.

## 7. 다중 인스턴스 Scale-out 시 중복 발행 가능성이 생기는 이유

**현재 구조 →** `CarePlanOutboxEventQueryRepositoryImpl.findByStatus()`는 단순 `SELECT` 쿼리(
`SpringDataCarePlanOutboxEventRepository.findByStatusOrderByCreatedAtAsc(status, pageable)`)이며, 행에 대한 어떤 잠금(락)도 걸지 않는다.
조회된 row를 "내가 처리하겠다"고 표시하는 중간 상태(예: `PROCESSING`)도 없다 — `PENDING`으로 조회한 뒤 곧바로 발행을 시도하고, 성공/실패 결과만 사후에 반영한다.

**문제 발생 조건 →** care-plan-service가 인스턴스 A, B 두 대로 스케일아웃되어 있고, 두 인스턴스의 `CarePlanOutboxRelayScheduler`가 (완전히 동기화되어 있지 않으므로)
거의 같은 시각에 각자의 폴링 주기를 실행하면, 두 인스턴스 모두 `findByStatus(PENDING, 100)`으로 **동일한 PENDING row 집합**을 조회할 수 있다.

**영향 →** 두 인스턴스 모두 같은 이벤트를 `carePlanCompletedEventPort.publish(event)`로 RabbitMQ에 발행한다. `markSent()`는 멱등적으로 상태만 `SENT`로
바꾸므로 두 번째 호출도 예외 없이 성공하지만, **RabbitMQ에는 동일한 이벤트가 최소 2번 전달된다.** 이를 소비하는 쪽(예: social-worker-service, provider-service)이 멱등
처리를 하지 않는다면 동일 알림이 중복 발송되는 등 부수효과가 중복 실행될 수 있다.

## 8. `FOR UPDATE SKIP LOCKED`와 `PENDING → PROCESSING` 선점 방식의 차이

| 구분         | `FOR UPDATE SKIP LOCKED`                                                               | `PENDING → PROCESSING` 상태 선점                                                                                                                    |
|------------|----------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------|
| 동작 방식      | 조회 쿼리에 DB row-level 락을 걸되, 이미 다른 트랜잭션이 잠근 행은 건너뛰고(`SKIP LOCKED`) 잠기지 않은 행만 반환          | 애플리케이션이 먼저 `UPDATE ... SET status = 'PROCESSING' WHERE status = 'PENDING' AND id IN (...)` 같은 조건부 UPDATE를 실행해, 실제로 갱신에 성공한 row만 "내가 선점했다"고 간주   |
| 락 유지 범위    | 조회한 트랜잭션이 커밋/롤백될 때까지만 락이 유지되며 자동 해제됨                                                   | 명시적인 DB 락이 아니라 상태값 자체로 선점을 표현 — 별도 트랜잭션 경계 관리가 필요                                                                                               |
| 장애 복구      | 트랜잭션이 비정상 종료되면 락도 자동 해제되어 다른 인스턴스가 곧바로 이어받을 수 있음                                       | 인스턴스가 `PROCESSING`으로 바꾼 뒤 죽어버리면 그 row는 영원히 `PROCESSING`에 머무를 수 있음 — 별도의 타임아웃 기반 복구 로직(예: "일정 시간 이상 PROCESSING인 row는 다시 PENDING으로 되돌린다")이 추가로 필요 |
| 구현 난이도/이식성 | JPQL/QueryDSL에서 기본적으로 지원 범위가 제한적이라 네이티브 쿼리가 필요할 수 있고, DB 벤더별 문법 차이가 있음(PostgreSQL은 지원) | 표준 UPDATE 문이므로 벤더 중립적이고 이해하기 쉬움                                                                                                                 |
| 현재 코드와의 거리 | `CarePlanOutboxEventQueryRepositoryImpl`을 네이티브/락 힌트 쿼리로 재작성해야 함                        | 기존 `CarePlanOutboxEvent`에 상태 하나(`PROCESSING`)를 추가하고 조회 로직을 "조건부 UPDATE 후 그 결과만 재조회"하는 흐름으로 바꿔야 함                                                |

두 방식 모두 현재 코드(`CarePlanOutboxEventQueryRepositoryImpl.findByStatus`, `SpringDataCarePlanOutboxEventRepository`)에는 구현되어
있지 않으며, 어느 쪽을 택하든 지금 없는 기능을 새로 추가하는 작업이다.

## 9. 실제 구현 결과 — PENDING → PROCESSING 선점 (다중 인스턴스 중복 발행 방지)

8장의 비교표 중 **`PENDING → PROCESSING` 선점 방식**을 사용자가 선택해 구현했다. 다만 "조건부 UPDATE"의 원자성은 8장에서 언급한 벌크 SQL이 아니라 **JPA `@Version`(낙관적 락)** 으로 구현했다 — 기존 코드가 전부 "엔티티를 `findById`로 읽고, 도메인 메서드를 호출하고, `save()`한다"는 스타일(`markSent()`/`recordFailure()`와 동일)을 그대로 따르면서, DB 벤더 중립적인 표준 JPA 메커니즘만으로 선점 원자성을 얻을 수 있기 때문이다. 네이티브 SQL이나 별도 `@Modifying` 벌크 쿼리를 추가하지 않았다.

### 변경된 상태 모델

```java
// careplan/domain/entity/CarePlanOutboxEventStatus.java
public enum CarePlanOutboxEventStatus {
    PENDING,
    PROCESSING,   // 신규 — 어떤 인스턴스가 발행을 시도 중임을 표시
    SENT,
    FAILED
}
```

`CarePlanOutboxEvent`에 `@Version private long version;` 컬럼을 추가했다(`docker/postgres/care-plan-service.sql`에 `version BIGINT NOT NULL DEFAULT 0` 컬럼과, `care_plan_outbox_event_status` enum에 `PROCESSING` 값 추가). 도메인 메서드로 `isPending()`, `startProcessing()`, `revertStuckProcessing()`을 추가했다.

### 선점(claim) 흐름

```
CarePlanOutboxRelayFacade.relayOne(pendingEvent)
   ├─ tryClaim(outboxEventId)
   │    └─ CarePlanOutboxCommandService.claim(outboxEventId)   [@Transactional]
   │         ├─ findById(id) → status != PENDING 이면 false 반환 (이미 다른 인스턴스가 선점/처리 완료)
   │         ├─ event.startProcessing()  → status = PROCESSING
   │         └─ save(event)
   │              └─ 커밋 시점에 DB의 version과 내가 읽은 version이 다르면
   │                 (= 그 사이 다른 인스턴스가 먼저 선점해 커밋함)
   │                 ObjectOptimisticLockingFailureException 발생
   │
   ├─ claim 성공(true) → 기존과 동일하게 publish() → markSent()/recordFailure()
   └─ claim 실패(false 반환 또는 낙관적 락 예외) → 조용히 skip, 이 인스턴스는 발행을 시도하지 않음
```

`CarePlanOutboxRelayFacade.tryClaim()`이 `ObjectOptimisticLockingFailureException`을 잡아 `false`로 변환하므로, `relayOne()` 입장에서는 "이미 다른 인스턴스가 선점함"과 "애초에 PENDING이 아니었음"이 동일하게 취급된다 — 둘 다 이 인스턴스가 처리하지 않아야 한다는 의미이기 때문이다.

### 방치된 PROCESSING 복구 (Stuck Recovery)

선점(PROCESSING) 이후 `markSent()`/`recordFailure()` 없이 인스턴스가 죽으면 그 row는 영원히 `PROCESSING`에 머무를 수 있다는 8장의 지적을 그대로 반영해, 복구 로직을 함께 구현했다.

- `CarePlanOutboxRelayFacade.relay()`는 `findPending()` 조회 **전에** 항상 `reclaimStuckProcessing()`을 먼저 호출한다.
- `CarePlanOutboxQueryService.findStuckProcessing(threshold, limit)` → `CarePlanOutboxEventQueryRepository.findStuckProcessing()` → `SpringDataCarePlanOutboxEventRepository.findByStatusAndUpdatedAtBeforeOrderByUpdatedAtAsc(PROCESSING, threshold, ...)`로, `updatedAt`이 임계값보다 오래된 `PROCESSING` row를 찾는다.
- 찾은 각 row에 대해 `CarePlanOutboxCommandService.revertStuckProcessing(id)`가 `PENDING`으로 되돌린다(이 되돌리기 역시 `@Version` 대상이므로, 두 인스턴스가 동시에 같은 stuck row를 복구하려 해도 하나만 성공한다 — 실패하는 쪽은 무시).
- 임계값은 `CarePlanOutboxRelayFacade.STUCK_PROCESSING_THRESHOLD = Duration.ofMinutes(1)`로 하드코딩했다 — 기존 `BATCH_SIZE = 100`과 동일하게, 설정 프로퍼티로 빼지 않고 상수로 두는 이 클래스의 기존 스타일을 그대로 따랐다.

### 테스트 작성 중 발견한 실제 버그와 수정

`CarePlanOutboxConcurrencyIntegrationTest`를 처음 작성했을 때 `retryFailed_thenRelay_reachesSent`/`findStuckProcessing_thenRevert_recoversStuckRow` 테스트가 간헐적으로 `ObjectOptimisticLockingFailureException`으로 실패했다. 원인은 테스트 코드가 아니라 **실제 운영 코드의 정상 동작**이었다 — 이 서비스는 이미 `@SpringBootTest` 컨텍스트 안에서 실제 `CarePlanOutboxRelayScheduler`가 5초 간격으로 살아 움직이고 있고, 테스트가 수동으로 `claim()`/`revertStuckProcessing()`을 호출하는 도중에 **진짜 백그라운드 스케줄러가 같은 row를 향해 자기 자신의 `relay()` 사이클을 돌리며 실제로 경합**한 것이다. 이는 오히려 이번에 구현한 낙관적 락이 의도대로 동작하고 있다는 방증이기도 하다. 다만 이 특정 테스트는 "내가 의도한 순서대로" 선점/복구를 검증해야 하므로, `@SpringBootTest(properties = "care-plan.outbox.relay.enabled=false")`로 이 테스트 클래스에서만 백그라운드 스케줄러를 꺼서 결정적으로 만들었다(다중 인스턴스 경합 자체는 `claim_concurrentClaim_onlyOneInstanceWins`에서 의도적으로 재현한다).

### 운영 유의사항

- DB 마이그레이션: `docker/postgres/care-plan-service.sql`의 `care_plan_outbox_event_status` enum에 `PROCESSING`을, 테이블에 `version BIGINT NOT NULL DEFAULT 0`을 추가했다. 09번 문서에서 이미 다룬 것과 동일한 이유로, 이미 떠 있는 브로커/DB에 이 스키마가 없다면 로컬 개발 DB는 재생성이 필요하고, 실제 운영 반영 시에는 `ALTER TYPE ... ADD VALUE 'PROCESSING'`과 `ALTER TABLE ... ADD COLUMN version BIGINT NOT NULL DEFAULT 0`을 별도 마이그레이션으로 적용해야 한다(`ddl-auto: validate`인 prod 환경은 자동 반영되지 않음).
- `STUCK_PROCESSING_THRESHOLD`(1분)는 하드코딩된 상수이므로, 운영 중 값을 조정하려면 코드 수정이 필요하다. 이번 범위에서는 `BATCH_SIZE`와의 일관성을 위해 상수로 유지했다.
