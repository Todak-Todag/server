# 12. Outbox 운영 안정성

> 관련 이슈: [Feat] CarePlan 이벤트 발행·소비 안정성 및 정합성 개선 #283
>
> 이 문서는 Outbox(`p_care_plan_outbox_events`) 운영 안정성의 **현재 구현 상태**를 설명한다. 대상 클래스:
`careplan/domain/entity/CarePlanOutboxEvent.java`, `careplan/application/facade/CarePlanOutboxRelayFacade.java`,
`careplan/infrastructure/messaging/CarePlanOutboxRelayScheduler.java`,
`careplan/application/service/command/CarePlanOutboxCommandService.java`,
`careplan/application/service/query/CarePlanOutboxQueryService.java`.

## 1. 상태 모델과 전이

```java
// careplan/domain/entity/CarePlanOutboxEventStatus.java
public enum CarePlanOutboxEventStatus {
    PENDING,     // 발행 대기
    PROCESSING,  // 어떤 인스턴스가 선점해 발행을 시도 중
    SENT,        // 발행 성공
    FAILED       // 최대 재시도 초과, 자동 처리 대상에서 제외
}
```

`CarePlanOutboxEvent`의 전이:

| 메서드                                                   | 전이                                                                                                          | 비고                                     |
|-------------------------------------------------------|-------------------------------------------------------------------------------------------------------------|----------------------------------------|
| `create(aggregateId, eventType, payload)`             | → `PENDING`                                                                                                 | `retryCount = 0`                       |
| `claim()`(`CarePlanOutboxCommandService.claim()`이 호출) | `PENDING` → `PROCESSING`                                                                                    | `@Version` 낙관적 락으로 선점 (2장)             |
| `markSent()`                                          | `PROCESSING` → `SENT`                                                                                       | `publishedAt` 기록                       |
| `recordFailure(errorMessage)`                         | `PROCESSING` → `PENDING`(`retryCount < 3`) 또는 `PROCESSING` → `FAILED`(`retryCount >= 3`, `MAX_RETRY_COUNT`) | `retryCount` 증가, `lastErrorMessage` 기록 |
| `revertStuckProcessing()`                             | `PROCESSING` → `PENDING`                                                                                    | stuck recovery (3장)                    |

## 2. 다중 인스턴스 동시 선점 방지

`CarePlanOutboxRelayFacade.relayOne()`은 발행을 시도하기 전에 `CarePlanOutboxCommandService.claim(outboxEventId)`로
`PENDING → PROCESSING` 선점을 시도한다.

- 이미 `PENDING`이 아니면 `false`를 반환하고 발행을 시도하지 않는다.
- 두 인스턴스가 같은 row를 동시에 선점하려 하면, `CarePlanOutboxEvent`의 `@Version` 컬럼에 의해 먼저 커밋한 쪽만 성공하고 나머지는
  `ObjectOptimisticLockingFailureException`이 발생한다. `CarePlanOutboxRelayFacade.tryClaim()`이 이 예외를 잡아 조용히 스킵 처리한다.
- 이 두 경우(애초에 PENDING이 아니었던 경우/낙관적 락 충돌) 모두 "이 인스턴스가 처리하지 않아야 한다"는 동일한 결과로 취급된다.

동시에 같은 PENDING 이벤트를 선점해서 중복 발행하는 경우를 방지한다.

## 3. Stuck PROCESSING 복구

선점(`PROCESSING`) 이후 `markSent()`/`recordFailure()` 없이 인스턴스가 죽으면 그 row는 `PROCESSING`에 방치될 수 있다.

- `CarePlanOutboxRelayFacade.relay()`는 매 폴링마다 `findPending()` 조회 **전에** `reclaimStuckProcessing()`을 먼저 실행한다.
- `CarePlanOutboxQueryService.findStuckProcessing(threshold, limit)`가 `updatedAt < threshold`인 `PROCESSING` row를 조회한다.
  `threshold = 현재 시각 - CarePlanOutboxRelayFacade.STUCK_PROCESSING_THRESHOLD`(1분, 상수).
- `CarePlanOutboxCommandService.revertStuckProcessing(outboxEventId, threshold)`는 재조회한 최신 엔티티에 대해
  `CarePlanOutboxEvent.isStuckProcessing(threshold)`(`status == PROCESSING && updatedAt < threshold`)를 **다시 검증한 뒤에만**
  `PENDING`으로 복구한다.
    - 조회와 복구 사이에 다른 인스턴스가 이미 복구 후 재선점했다면 `updatedAt`이 최신으로 갱신되어 이 재검증에서 걸러지므로, 정상 처리 중인 이벤트를 잘못 되돌리지 않는다.
    - 이 복구도 `@Version` 대상이라, 두 인스턴스가 동시에 같은 stuck row를 복구하려 해도 하나만 성공한다.

## 4. FAILED 처리

- 발행이 3회(`MAX_RETRY_COUNT`) 실패하면 `FAILED`로 전환된다.
- `FAILED`는 `findPending()` 조회 대상에서 제외되므로 이후 자동 재시도되지 않는다.
- row는 삭제되지 않고 `p_care_plan_outbox_events` 테이블에 그대로 보존된다.
- 최종 실패 시 `CarePlanOutboxCommandService.recordFailure()`가 다음 필드를 포함한 ERROR 로그를 남긴다.
  ```java
  log.error(
          "[CarePlan] Outbox 이벤트 최종 발행 실패 outboxEventId={} eventType={} aggregateId={} retryCount={} lastErrorMessage={}",
          event.getId(), event.getEventType(), event.getAggregateId(),
          event.getRetryCount(), event.getLastErrorMessage()
  );
  ```
- `FAILED` 수동 재처리 방식과 Outbox 데이터 보관/삭제 정책은 후속 과제로 `docs/technical-debt/TECH_DEBT.md` 6번 항목("Outbox FAILED 재처리 및 보관 정책
  미정")에 기록되어 있다.

## 6. 참고

- DB: `docker/postgres/care-plan-service.sql`의 `care_plan_outbox_event_status` enum에 `PROCESSING` 값, 테이블에
  `version BIGINT NOT NULL DEFAULT 0` 컬럼이 포함되어 있어야 한다.
- stuck recovery 임계값(`STUCK_PROCESSING_THRESHOLD = Duration.ofMinutes(1)`)은 `CarePlanOutboxRelayFacade`에 상수로 고정되어 있다(
  `BATCH_SIZE`와 동일한 스타일 — 설정 프로퍼티로 분리하지 않음).
- 남은 제한사항(수동 재처리, 데이터 보관/삭제 정책)은 `docs/technical-debt/TECH_DEBT.md` 참고.
