# 03. 서비스 일정 변경

| 항목 | 내용 |
|---|---|
| Method | `PATCH` |
| URL | `/api/v1/service-schedules/{serviceScheduleId}/status` |
| 사용자 | 퇴원예정자 |
| 카테고리 | 수정 |
| 테이블명 | `p_service_schedules` |

## 설명

퇴원 예정자가 본인에게 배정된 서비스 일정의 날짜를 변경한다.

## 비즈니스 규칙

- 일정 시작 **24시간 전까지**만 변경할 수 있다.
- 본인에게 배정된 서비스 일정만 변경할 수 있다.
- 서비스 일정의 `status`가 `SCHEDULED`인 경우에만 변경할 수 있다.
- 요청자의 `userId`와 `role`은 `@AuthenticationPrincipal UserContext user`를 통해 확인한다.
- 기존 일정 기준 **하루 앞당기기** 또는 **하루 미루기**만 가능하다.
- 일정 변경 시 `servicePreferenceId`를 기준으로 **care-plan-service에 Internal API를 호출**하여, 해당 서비스 희망 일정이 속한 Care Plan의 `carePlanId`와 `finishDate`를 조회한다. 조회한 `finishDate`는 "하루 미루기" 시 Care Plan의 일정 범위 초과 여부를 검증하는 데 사용한다.
   - schedule-service와 care-plan-service는 서로 다른 데이터 소유권을 가진 별도 서비스이므로(MSA 컨벤션 — `코드_컨벤션.md` 2장 참고), DB를 직접 조인하지 않고 `infrastructure/client/`의 Feign 클라이언트로 조회한다.
   - Internal API 호출이므로 `X-Internal-Api-Key` 헤더 기반 인증을 따른다 (`코드_컨벤션.md` 15장 참고).

### 처리 흐름

1. 일정 변경 요청을 받으면 `servicePreferenceId`를 기준으로 care-plan-service Internal API를 호출하여 `carePlanId`, `finishDate`를 조회한다.
2. 일정 변경 요청이 접수되면 해당 일정의 `status`를 `RESCHEDULING`으로 변경한다.
3. 변경할 날짜에 대해 `ProviderReMatched` Event를 발행한다. (Event에는 변경된 일정 날짜와 서비스를 포함)
4. 일정 변경 요청 처리와 Event 발행은 하나의 흐름으로 처리한다.
5. 일정 변경의 최종 결과는 해당 Event의 응답을 받아 처리한다.
   - 성공 시: `status` → `CHANGED`
   - 실패 시: `status` → `SCHEDULED` (복구)

> ⚠️ 확인 필요: 이 엔드포인트의 동기 응답은 `RESCHEDULING` 상태까지만 반환한다. 최종 결과(`CHANGED` 또는 복구된 `SCHEDULED`)를 클라이언트가 어떻게 확인하는지(폴링/알림 등)는 명시되어 있지 않음 — 팀 확인 필요.
>
> ⚠️ 확인 필요: care-plan-service Internal API 호출이 1번(사전 검증) 시점에만 이뤄지는지, 아니면 실패 시 복구 단계에서도 재조회가 필요한지 — 및 해당 API가 실패(care-plan-service 장애, Care Plan 미존재 등)했을 때의 에러 처리/상태 코드가 명시되어 있지 않음. 팀 확인 필요.

### 일정 변경 규칙

기존 서비스 일정 날짜를 `D`라고 할 때 다음 규칙을 적용한다.

| 변경 유형 | 변경 가능한 날짜 | 비고 |
|---|---|---|
| 하루 앞당기기 | `D - 1일` | 단, 변경일이 오늘인 경우 불가 |
| 하루 미루기 | `D + 1일` | Care Plan의 일정 범위(`finishDate`)를 초과할 수 없음 |

## Request

| key | 설명 | value 타입 | 위치 | 제약사항 | Nullable | 예시 |
|---|---|---|---|---|---|---|
| serviceScheduleId | 변경할 서비스 일정 ID | UUID | Path Variable | 존재하는 서비스 일정이어야 함 | X | `3fa85f64-5717-4562-b3fc-2c963f66afa6` |
| date | 변경할 일정 날짜 | Date | Body | 기존 일정 기준 하루 전 또는 하루 후만 가능 | X | `2026-08-29` |

## Response

| key | 설명 | value 타입 | 옵션 | Nullable | 예시 |
|---|---|---|---|---|---|
| serviceScheduleId | 변경된 서비스 일정 ID | UUID | - | X | `3fa85f64-5717-4562-b3fc-2c963f66afa6` |
| status | 일정 상태 | String(ENUM) | `SCHEDULED`, `RESCHEDULING`, `CHANGED`, `COMPLETED`, `CANCELED`, `NO_SHOW` | X | `RESCHEDULING` |

**Example**
```javascript
// 성공
{

  "code": 200,
  "message": "서비스 일정 변경 성공",
  "data": {

    "status": "RESCHEDULING"
  }
}

// 실패
{
  "success": false,
  "code": "SERVICE_SCHEDULE_NOT_FOUND",
  "message": "서비스 일정 변경 실패",
  "details": {
    "reason": "존재하지 않는 서비스 일정입니다."
  },
  "timestamp": "2026-08-27T10:00:00Z"
}
```

## Status

| status | response content |
|---|---|
| `200` | 서비스 일정 변경 성공 |
| `400` | 변경 날짜가 기존 일정 기준 하루 전/후가 아님 |
| `400` | 당일 일정으로 변경 시도 |
| `400` | `SCHEDULED` 상태가 아님 |
| `400` | 일정 시작 24시간 이내에 요청 |
| `400` | Care Plan 일정 범위를 초과 |
| `403` | 본인의 서비스 일정이 아님 |
| `404` | 서비스 일정이 존재하지 않음 |

## 변경 이력

| 날짜 | 변경 내용 |
