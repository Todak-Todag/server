# 03. 서비스 일정 변경

| 항목 | 내용 |
| --- | --- |
| Method | `PATCH` |
| URL | `/api/v1/service-schedules/{serviceScheduleId}/status` |
| 사용자 | 퇴원예정자 |
| 카테고리 | 수정 |
| 테이블명 | `p_service_schedules`, `p_schedule_outbox_events` |

## 설명

퇴원 예정자가 본인에게 배정된 서비스 일정의 날짜를 변경한다. 이 API는 변경을 **접수**만 하며, 실제 새 일정은 Provider-Service의 재매칭 결과 이벤트를 수신하면서 생성된다.

## 비즈니스 규칙

- 접근 권한은 `@PreAuthorize("hasRole('PATIENT')")`로 제한하며, 요청자의 `userId`는 `@AuthenticationPrincipal UserContext user`로 주입받는다.
- 일정 시작 **24시간 전까지**만 변경할 수 있다.
- 본인에게 배정된 서비스 일정만 변경할 수 있다.
- 서비스 일정의 `status`가 `SCHEDULED`인 경우에만 변경할 수 있다.
- 기존 일정 기준 **하루 앞당기기** 또는 **하루 미루기**만 가능하다.
- `servicePreferenceId`를 기준으로 **care-plan-service Internal API**(`GET /internal/v1/service-preferences/{servicePreferenceId}/care-plan`)를 호출해 `carePlanId`, `finishDate`, `patientId`를 조회한다. `patientId`는 소유권 검증에, `finishDate`는 "하루 미루기" 범위 검증에 쓴다.
    - schedule-service와 care-plan-service는 데이터 소유권이 분리되어 있으므로 DB 직접 조인이 아닌 `infrastructure/client/`의 Feign 클라이언트로 조회한다.
    - Internal API 호출이므로 `X-Internal-Api-Key` 헤더 기반 인증을 따르며, 헤더는 `FeignConfig`의 `RequestInterceptor`가 자동으로 붙인다.
    - 호출은 **접수 시점 1회**뿐이다. 재매칭 성공/실패 처리는 이벤트 수신 경로에서 이뤄지며 Care Plan을 재조회하지 않는다.
- **검증 순서**: 소유권(403) → 마감 시각(400) → 날짜 규칙(400) → 상태 전이(400). 비소유자가 400 응답으로 대상의 존재나 상태를 알아내지 못하게 하기 위해 소유권을 가장 먼저 본다.

### 처리 흐름

1. `serviceScheduleId`로 일정을 조회한다 (없거나 논리 삭제됐으면 `403`).
2. `servicePreferenceId`로 care-plan-service Internal API를 호출해 `carePlanId`, `finishDate`, `patientId`를 조회한다 (DB 트랜잭션 밖).
3. 트랜잭션 시작 — 일정을 **로우 쓰기 락으로 다시 조회**하고(`findByIdForUpdate`) 위 순서대로 검증한 뒤 `status`를 `RESCHEDULING`으로 전이한다.
4. `ProviderReMatched` 이벤트 페이로드를 만들어 **같은 트랜잭션에서 아웃박스에 적재**한다 (`aggregate_id = serviceScheduleId`).
    - 페이로드의 `regionId`/`provideServiceId`는 해당 `servicePreferenceId`의 **가장 최근 `MATCHED` 매칭 시도 레코드**에서 읽어온다. 이 레코드가 없으면 `404 SERVICE_MATCHING_ATTEMPT_NOT_FOUND`.
    - 이 경로에서는 시간대를 고르지 않으므로 `preferredTimeSlot`은 `null`이다.
5. 커밋 이후 아웃박스 릴레이(5초 주기 폴링)가 실제 브로커로 발행한다.
6. 최종 결과는 결과 이벤트 수신으로 확정된다.
    - 재매칭 성공(`ProviderMatched`): 이 일정은 `CHANGED`가 되고 **새 일정 레코드**가 `SCHEDULED`로 생성된다.
    - 재매칭 실패(`ProviderMatchFailed`): 이 일정이 `SCHEDULED`로 복구된다.

> 동기 응답은 `RESCHEDULING`까지만 반환한다. 최종 결과는 **클라이언트가 01/02번 조회로 확인**한다 — SSE 등 실시간 알림은 구현하지 않는다.
>

### 이중 클릭 방어는 대상 로우 쓰기 락으로

3번 단계의 재조회는 반드시 **쓰기 락**이어야 한다. 락 없이 읽으면 이중 클릭 시 두 요청이 모두 `SCHEDULED`를 읽고 통과해 같은 `servicePreferenceId`에 `RESCHEDULING` 일정이 2건 생긴다.

그러면 이후 매칭 결과 수신(13·14번)이 `RESCHEDULING` 일정을 1건으로 특정하지 못해 409 `SERVICE_SCHEDULE_MULTIPLE_RESCHEDULING`을 던지는데, **이 예외는 재시도로 해소되지 않아 메시지가 영구 DLQ로 간다.** 데이터를 손으로 고치기 전에는 그 일정이 영영 확정되지 않는다.

락을 잡으면 늦게 온 요청은 대기 후 `RESCHEDULING`을 읽어 `rescheduling()`의 기존 400(`SERVICE_SCHEDULE_INVALID_STATUS_FOR_RESCHEDULING`)으로 걸러진다. 잠글 로우(대상 일정)가 이미 존재하므로 advisory lock은 불필요하다.

> 16번(재매칭 시도)도 같은 이유로 같은 방식을 쓴다. 다만 16번은 동기 상태 변경이 없어 락 안에서 보는 값이 `status`가 아니라 **아웃박스 적재 여부**이며, 거절 응답도 400이 아니라 409다 — `16_재매칭시도.md` 참고.
>

### 일정 변경 규칙

기존 서비스 일정 날짜를 `D`라고 할 때 다음 규칙을 적용한다.

| 변경 유형 | 변경 가능한 날짜 | 비고 |
| --- | --- | --- |
| 하루 앞당기기 | `D - 1일` | 단, 변경일이 오늘인 경우 불가 |
| 하루 미루기 | `D + 1일` | Care Plan의 일정 범위(`finishDate`)를 초과할 수 없음 |

## Request

| key | 설명 | value 타입 | 위치 | 제약사항 | Nullable | 예시 |
| --- | --- | --- | --- | --- | --- | --- |
| serviceScheduleId | 변경할 서비스 일정 ID | UUID | Path Variable | 존재하는 서비스 일정이어야 함 | X | `3fa85f64-5717-4562-b3fc-2c963f66afa6` |
| date | 변경할 일정 날짜 | LocalDate | Body | `@NotNull`, 기존 일정 기준 하루 전 또는 하루 후만 가능 | X | `2026-08-29` |

## Response

| key | 설명 | value 타입 | 옵션 | Nullable | 예시 |
| --- | --- | --- | --- | --- | --- |
| serviceScheduleId | 변경 접수된 서비스 일정 ID | UUID | - | X | `3fa85f64-5717-4562-b3fc-2c963f66afa6` |
| status | 일정 상태 | String(ENUM) | 접수 성공 시 항상 `RESCHEDULING` | X | `RESCHEDULING` |

**Example**

```jsx
// 성공
{
    "success": true,
    "code": 200,
    "message": "서비스 일정 변경 성공",
    "data": {
    "serviceScheduleId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
        "status": "RESCHEDULING"
}
}

// 실패
{
    "success": false,
    "code": "AUTH_FORBIDDEN",
    "message": "요청 권한이 없습니다.",
    "details": {
    "reason": "요청 권한이 없습니다."
},
    "timestamp": "2026-08-27T10:00:00Z"
}
```

## Status

| status | ErrorCode | response content |
| --- | --- | --- |
| `200` | - | 서비스 일정 변경 접수 성공 |
| `400` | `SERVICE_SCHEDULE_INVALID_RESCHEDULE_DATE` | 변경 날짜가 기존 일정 기준 하루 전/후가 아님 |
| `400` | `SERVICE_SCHEDULE_RESCHEDULE_TO_TODAY_NOT_ALLOWED` | 당일 일정으로 변경 시도 |
| `400` | `SERVICE_SCHEDULE_RESCHEDULE_EXCEEDS_CARE_PLAN_RANGE` | Care Plan 일정 범위(`finishDate`) 초과 |
| `400` | `SERVICE_SCHEDULE_DELAY_DEADLINE_EXCEEDED` | 일정 시작 24시간 이내에 요청 |
| `400` | `SERVICE_SCHEDULE_INVALID_STATUS_FOR_RESCHEDULING` | `SCHEDULED` 상태가 아님 |
| `400` | `INVALID_PARAMETER` | `date` 누락/형식 오류 등 Validation 실패 |
| `403` | `AUTH_FORBIDDEN` | 본인의 서비스 일정이 아니거나, 존재하지 않는 서비스 일정 (리소스 존재 여부 비노출) |
| `404` | `SERVICE_MATCHING_ATTEMPT_NOT_FOUND` | 이벤트 페이로드에 필요한 `MATCHED` 매칭 시도 기록이 없음 |
| `500` | `EXTERNAL_SERVICE_CALL_REJECTED` | care-plan-service가 404 외 4xx로 요청을 거부 |
| `502` | `EXTERNAL_SERVICE_RESPONSE_INVALID` | care-plan-service 응답을 역직렬화하지 못했거나 필수 필드가 비어 옴 |
| `503` | `EXTERNAL_SERVICE_UNAVAILABLE` | care-plan-service 연결 실패·타임아웃, 또는 상대 서비스가 5xx 반환 |

> care-plan-service가 `404`(없는 `servicePreferenceId`)를 반환하면 `403 AUTH_FORBIDDEN`으로 변환된다 — 리소스 존재 여부 비노출 정책과 같은 취급이다. 원인별 변환 규칙은 `schedule-service.md` 5.6절 "호출 실패 처리 (5.5·5.6 공통)" 참고.
