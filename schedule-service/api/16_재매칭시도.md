# 16. 재매칭 시도

| 항목 | 내용 |
| --- | --- |
| Method | `POST` |
| URL | `/api/v1/matching-attempts/{matchingAttemptId}/retry` |
| 사용자 | 퇴원예정자 |
| 카테고리 | 등록 |
| 테이블명 | `p_service_matching_attempts` |

## 설명

가장 최근 매칭이 **실패(`FAILED`)** 한 서비스 희망 일정에 대해, 퇴원 예정자가 새로운 희망 날짜/시간대를 선택하여 재매칭을 시도한다.

이미 매칭에 성공해 서비스 일정(`p_service_schedules`)이 생성된 이후의 일정 변경은 **03번(서비스 일정 변경) API**를 사용하며, 본 API는 **아직 서비스 일정이 생성되지 않은 것에만(최초 매칭 실패)** 사용한다.

> 이로써 14번 문서에서 확인 필요로 남겨뒀던 "초기 매칭 실패 시 `p_service_schedules`에 취소할 대상이 있는지" 의문이 해소된다 — **초기 매칭 실패 시점에는 `p_service_schedules` 레코드 자체가 아직 없다.** `ProviderMatchFailed` 이벤트 수신 시 초기 실패 케이스라면 `p_service_matching_attempts`에만 기록하고 `p_service_schedules`는 건드리지 않는 것이 맞다.
>

## 비즈니스 규칙

- `matchingAttemptId`로 재시도할 대상 매칭 시도를 지정하며, 해당 시도의 `status`가 `FAILED`인 경우에만 재시도할 수 있다.
- 요청자의 `userId`와 `role`은 `@AuthenticationPrincipal UserContext user`를 통해 확인한다.
- 대상 매칭 시도의 `servicePreferenceId`를 기준으로 care-plan-service Internal API를 호출하여, 해당 서비스 희망 일정이 속한 Care Plan을 조회한다 — 권한 검증에 필요한 `patientId`와 날짜 범위 검증에 필요한 `startDate`/`finishDate`를 확인한다.
    - ⚠️ 확인 필요 (신규, 중요): 03/04번 문서에서 확인된 care-plan-service Internal API는 `carePlanId`/`finishDate`/`patientId` **3개 필드**만 반환하는 것으로 확정되어 있었다(`schedule-service.md` 5.5절). 그런데 이 API는 **`startDate`도 추가로 필요**하다. 같은 API의 응답에 `startDate`가 이미 포함되어 있었는데 그동안 03/04번에서는 언급이 없었던 것인지, 아니면 이 API를 위해 응답 필드를 확장해야 하는지 확인이 필요하다.
- 본인에게 배정된 서비스 희망 일정의 매칭 시도만 재시도할 수 있다.
- 재매칭 희망 날짜는 Care Plan의 `start_date`~`finish_date` 범위 내여야 한다.
- 요청이 접수되면 기존 매칭 시도의 `carePlanId`, `regionId`, `provideServiceId`, `servicePreferenceId`와 새로 입력된 `date`, `preferredTimeSlot`을 조합하여 `ProviderRematched` 이벤트를 아웃박스 패턴으로 발행한다.
    - 이로써 12번 문서에서 확인 필요로 남겨뒀던 "`ProviderRematched` 페이로드의 `regionId`/`provideServiceId` 출처"가 이 API 경로에 한해서는 해소된다 — **기존(실패한) 매칭 시도 레코드에서 그대로 읽어온다.** 다만 03번(일정 변경) 경로로 발행될 때는 여전히 출처가 불명확하므로, 그 경우엔 아마도 해당 일정의 가장 최근 `MATCHED` 매칭 시도 레코드에서 조회하는 방식일 것으로 추정되나 확정된 바는 아니다.
- 본 API 자체는 동기적으로 새로운 데이터를 생성하지 않으며(이벤트 발행만 수행), 실제 매칭 결과(성공/실패)는 Provider-Service가 발행한 `ProviderMatched`/`ProviderMatchFailed` 이벤트를 수신하면서 새로운 매칭 시도 이력으로 추가된다.
- 재시도 결과는 15번(매칭 실패 내역 조회) API를 통해 확인한다.

## Request

| key | 설명 | value 타입 | 위치 | 제약사항 | Nullable | 예시 |
| --- | --- | --- | --- | --- | --- | --- |
| matchingAttemptId | 재시도할 매칭 시도 ID | UUID | Path Variable | 존재하는 매칭 시도이며 status가 FAILED여야 함 | X | `3fa85f64-5717-4562-b3fc-2c963f66afa6` |
| date | 재매칭 희망 날짜 | LocalDate | Body | Care Plan 일정 범위(`start_date`~`finish_date`) 내여야 함 | X | `2026-09-10` |
| preferredTimeSlot | 재매칭 희망 시간대 | Enum(String) | Body | `MORNING`, `AFTERNOON`만 가능 | O | `MORNING` |

## Response

| key | 설명 | value 타입 | 옵션 | Nullable | 예시 |
| --- | --- | --- | --- | --- | --- |
| matchingAttemptId | 재시도 대상이 된 기존(실패) 매칭 시도 ID | UUID | - | X | `3fa85f64-5717-4562-b3fc-2c963f66afa6` |
| servicePreferenceId | 서비스 희망 일정 ID | UUID | - | X | `3f2504e0-4f89-41d3-9a0c-0305e82c3301` |
| date | 재전송된 재매칭 희망 날짜 | LocalDate | - | X | `2026-09-10` |
| preferredTimeSlot | 재전송된 재매칭 희망 시간대 | String(ENUM) | `MORNING`, `AFTERNOON` | O | `MORNING` |

**Example**

```jsx
// 성공
{
  "success": true,
  "code": 202,
  "message": "재매칭 시도 접수 성공",
  "data": {
    "matchingAttemptId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
    "servicePreferenceId": "3f2504e0-4f89-41d3-9a0c-0305e82c3301",
    "date": "2026-09-10",
    "preferredTimeSlot": "MORNING"
  }
}

// 실패
{
  "success": false,
  "code": "MATCHING_ATTEMPT_NOT_RETRYABLE",
  "message": "재매칭 시도 실패",
  "details": {
    "reason": "해당 매칭 시도는 FAILED 상태가 아니어 재시도할 수 없습니다."
  },
  "timestamp": "2026-09-07T10:00:00Z"
}
```

## Status

| status | response content |
| --- | --- |
| `202` | 재매칭 시도 접수 성공 (비동기 처리, 결과는 15번 API로 확인) |
| `400` | 재매칭 희망 날짜가 Care Plan 일정 범위를 초과 |
| `400` | Validation 실패 (날짜 형식 오류 등) |
| `403` | 본인의 서비스 희망 일정에 대한 매칭 시도가 아님 |
| `404` | 존재하지 않는 매칭 시도 |
| `409` | 매칭 시도 상태가 `FAILED`가 아닌 경우 (이미 재시도 중이거나 매칭에 성공한 경우) |
