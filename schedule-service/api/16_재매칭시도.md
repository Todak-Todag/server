# 16. 재매칭 시도

| 항목 | 내용 |
| --- | --- |
| Method | `POST` |
| URL | `/api/v1/matching-attempts/{matchingAttemptId}/retry` |
| 사용자 | 퇴원예정자 |
| 카테고리 | 등록 |
| 테이블명 | `p_service_matching_attempts`(조회), `p_schedule_outbox_events`(적재) |

## 설명

매칭이 **실패(`FAILED`)** 한 서비스 희망 일정에 대해, 퇴원 예정자가 새로운 희망 날짜/시간대를 선택하여 재매칭을 시도한다.

이미 매칭에 성공해 서비스 일정(`p_service_schedules`)이 생성된 이후의 일정 변경은 **03번(서비스 일정 변경) API**를 사용하며, 본 API는 **아직 서비스 일정이 생성되지 않은 것(최초 매칭 실패)** 에만 사용한다.

> 초기 매칭 실패 시점에는 `p_service_schedules` 레코드 자체가 없다. 그래서 14번(`ProviderMatchFailed` 수신)은 초기 실패 케이스에서 `p_service_matching_attempts`에만 기록하고 일정 테이블은 건드리지 않는다.
>

## 비즈니스 규칙

- 접근 권한은 `@PreAuthorize("hasRole('PATIENT')")`로 제한하며, 요청자의 `userId`는 `@AuthenticationPrincipal UserContext user`로 주입받는다.
- `matchingAttemptId`로 재시도할 대상 매칭 시도를 지정하며, 해당 시도의 `status`가 `FAILED`인 경우에만 재시도할 수 있다(`409`).
- 대상 매칭 시도의 `servicePreferenceId`를 기준으로 **care-plan-service Internal API**(`GET /internal/v1/service-preferences/{servicePreferenceId}/care-plan`)를 호출해 `carePlanId`/`finishDate`/`patientId`를 조회한다. `patientId`로 소유권을, `finishDate`로 날짜 범위를 검증한다. 호출은 **DB 트랜잭션 밖**에서 수행한다.
- 본인에게 배정된 서비스 희망 일정의 매칭 시도만 재시도할 수 있다.
- **검증 순서**: 소유권(403) → 재시도 가능 상태(409) → 중복 접수(409) → 날짜 범위(400). 비소유자가 409/400 응답으로 대상의 존재나 상태를 알아내지 못하게 하기 위해 소유권을 가장 먼저 본다.
- 재매칭 희망 날짜는 Care Plan의 `startDate`~`finishDate` 범위 내여야 한다(양끝 포함).
- 요청이 접수되면 기존 매칭 시도의 `carePlanId`, `regionId`, `provideServiceId`, `servicePreferenceId`와 새로 입력된 `date`, `preferredTimeSlot`을 조합해 `ProviderRematched` 이벤트를 **아웃박스에 적재**한다(`aggregate_id = matchingAttemptId`). 실제 발행은 릴레이가 수행한다.
- 본 API는 **동기적으로 새로운 데이터를 생성하지 않는다** — 그래서 응답이 `202 ACCEPTED`다. 새 매칭 시도 이력은 Provider-Service가 발행한 `ProviderMatched`/`ProviderMatchFailed`를 수신하면서 추가된다.
- 재시도 결과는 15번(매칭 실패 내역 조회) API로 확인한다.

### `startDate` 역산

care-plan-service Internal API 응답에는 **`startDate`가 없다**(`carePlanId`/`finishDate`/`patientId` 3개 필드). Care Plan 기간이 **30일 고정**이라는 점을 이용해 아래와 같이 역산한다.

```
startDate = finishDate - 29일        // CARE_PLAN_PERIOD_DAYS = 30
범위 판정  = startDate <= date <= finishDate
```

**care-plan-service 코드로 근거를 확인했다 (2026-09-08).** `CarePlanCommandService`가 `CARE_PLAN_PERIOD_DAYS = 30L`로 `startDate = 퇴원일 + 1일`, `finishDate = startDate + 29일`을 계산하고 있어 역산식이 정확히 일치한다. 응답 DTO(`CarePlanFindByPreferenceResponse`)에 `startDate`가 없다는 점도 확인했다.

Care Plan 기간이 가변으로 바뀌면 Internal API 응답에 `startDate`를 추가해야 한다.

### ⚠️ 확인 필요 (신규, 2026-09-08): 미래 날짜 검증 누락

**이 API는 희망 날짜가 미래인지 검증하지 않는다.** `MatchingAttemptValidator.validateRetryDate`는 Care Plan 범위(`startDate`~`finishDate`)만 확인하는데, Care Plan은 퇴원일 다음 날부터 시작하므로 **오늘 이전 날짜도 범위 안에 들어올 수 있다.**

이 경우 아래처럼 요청이 조용히 사라진다.

```
16번 호출(과거/당일 날짜) → 200/202 접수 → ProviderRematched 발행
  → provider-service는 그 날짜로 매칭 성공 → ProviderMatched 발행
  → schedule 수신 → ServiceSchedule.confirm의 "date는 오늘 이후" 불변식 위반
  → INVALID_PARAMETER → 리스너가 로그만 남기고 메시지 폐기 → 일정이 생성되지 않음
```

care-plan-service는 희망 일정 최초 등록 시 `ServicePreferenceDateValidator`로 `preferredDate > today`를 강제하고 있으므로, **이 API에도 같은 검증을 추가**해야 계약이 맞는다.

### 중복 접수(409) 판별

이 API는 동기적으로 아무 상태도 바꾸지 않으므로 `status`로는 "재시도 중"을 표현할 수 없다. 대신 **아웃박스에 같은 `matchingAttemptId`로 `ProviderReMatched`가 이미 적재됐는지**로 판별한다.

```
EXISTS (event_type = 'ProviderReMatched' AND aggregate_id = :matchingAttemptId)
  → 409 MATCHING_ATTEMPT_RETRY_ALREADY_REQUESTED
```

> 아웃박스 레코드는 발행 후에도 `SENT`로 남으므로, 한 매칭 시도에 대한 재시도는 **1회로 제한**된다. 재시도가 또 실패하면 새로 생성된 `FAILED` 이력(새 `matchingAttemptId`)을 대상으로 다시 호출한다.
>

## Request

| key | 설명 | value 타입 | 위치 | 제약사항 | Nullable | 예시 |
| --- | --- | --- | --- | --- | --- | --- |
| matchingAttemptId | 재시도할 매칭 시도 ID | UUID | Path Variable | 존재하는 매칭 시도이며 `status`가 `FAILED`여야 함 | X | `3fa85f64-5717-4562-b3fc-2c963f66afa6` |
| date | 재매칭 희망 날짜 | LocalDate | Body | `@NotNull`, Care Plan 일정 범위(`startDate`~`finishDate`) 내 | X | `2026-09-10` |
| preferredTimeSlot | 재매칭 희망 시간대 | Enum(String) | Body | `MORNING`, `AFTERNOON`만 가능 | O | `MORNING` |

## Response

| key | 설명 | value 타입 | 옵션 | Nullable | 예시 |
| --- | --- | --- | --- | --- | --- |
| matchingAttemptId | 재시도 대상이 된 기존(실패) 매칭 시도 ID | UUID | - | X | `3fa85f64-5717-4562-b3fc-2c963f66afa6` |
| servicePreferenceId | 서비스 희망 일정 ID | UUID | - | X | `3f2504e0-4f89-41d3-9a0c-0305e82c3301` |
| date | 재전송된 재매칭 희망 날짜 | LocalDate | - | X | `2026-09-10` |
| preferredTimeSlot | 재전송된 재매칭 희망 시간대 | String(ENUM) | `MORNING`, `AFTERNOON` | O | `MORNING` |


## Status

> ⚠️ **차단 (신규, 2026-09-08)**: **api-gateway 라우트에 `/api/v1/matching-attempts/**`가 등록되어 있지 않다.** 이 API는 게이트웨이를 통해 호출할 수 없다(404). 15번도 같은 문제이며, 게이트웨이 라우트 추가가 필요하다.
>

| status | ErrorCode | response content |
| --- | --- | --- |
| `202` | - | 재매칭 시도 접수 성공 (비동기 처리, 결과는 15번 API로 확인) |
| `400` | `MATCHING_ATTEMPT_RETRY_EXCEEDS_CARE_PLAN_RANGE` | 재매칭 희망 날짜가 Care Plan 일정 범위를 벗어남 |
| `400` | `INVALID_PARAMETER` | `date` 누락/형식 오류, `preferredTimeSlot`이 허용되지 않는 값 |
| `403` | `AUTH_FORBIDDEN` | 본인의 서비스 희망 일정이 아니거나, 존재하지 않는 매칭 시도 (리소스 존재 여부 비노출) |
| `409` | `MATCHING_ATTEMPT_NOT_RETRYABLE` | 매칭 시도 상태가 `FAILED`가 아님 (이미 매칭에 성공한 경우) |
| `409` | `MATCHING_ATTEMPT_RETRY_ALREADY_REQUESTED` | 같은 매칭 시도로 이미 재시도가 접수됨 |
