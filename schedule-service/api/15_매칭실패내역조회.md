# 15. 매칭 실패 내역 조회

| 항목 | 내용 |
| --- | --- |
| Method | `GET` |
| URL | `/api/v1/matching-attempts` |
| 사용자 | 퇴원예정자 |
| 카테고리 | 검색 |
| 테이블명 | `p_service_matching_attempts` |

## 설명

퇴원 예정자가 자신의 서비스 희망 일정에 대한 매칭 시도(성공/실패) 내역을 조회한다.

## 비즈니스 규칙

- 접근 권한은 `@PreAuthorize("hasRole('PATIENT')")`로 제한하며, 요청자의 `userId`는 `@AuthenticationPrincipal UserContext user`로 주입받는다.
- 조회 전에 **Care Plan 상태를 먼저 확인**한다. care-plan-service Internal API(`GET /internal/v1/care-plans/{patientId}`)로 조회한 상태가 `CONFIRMED`가 아니면 재매칭이 의미가 없으므로 **빈 페이지를 반환**한다.
  - 상대 API가 Care Plan 미존재/검토 중일 때 던지는 예외는 감추지 않고 그대로 전파한다.
  - 알 수 없는 상태 값(상대 서비스가 ENUM을 확장한 경우)은 `CONFIRMED`가 아닌 것으로 취급한다.
- care-plan-service Internal API(`GET /internal/v1/service-preferences?patientId=`)로 담당하는 모든 `servicePreferenceId` 목록을 조회한 뒤, 그 목록을 `IN` 조건으로 걸어 매칭 시도 내역을 조회한다. **소유 ID가 0건이면 DB를 조회하지 않고 빈 페이지를 반환한다.**
- 매칭 시도는 `ProviderMatched`/`ProviderMatchFailed` 이벤트를 수신할 때마다 새로운 이력으로 **누적(append)** 되며, 하나의 `servicePreferenceId`에 여러 건의 시도 내역이 존재할 수 있다.
- 상태(`status`)로 필터링 가능하며, 별도 지정이 없으면 **`FAILED`가 기본값**이다.
- 정렬은 최신순/오래된순만 가능하다 (정렬 필드는 `createdAt` 고정, 기본값 `createdAt,DESC`).
- 논리 삭제된 이력은 제외한다.

### `FAILED` 조회 시 추가 필터

`FAILED`로 조회할 때만 "해당 `servicePreferenceId`로 생성된 서비스 일정이 **아직 하나도 없는**" 조건을 함께 적용한다. `MATCHED`로 조회할 때는 적용하지 않는다.

```sql
-- FAILED 조회 시에만 추가되는 조건
NOT EXISTS (
  SELECT 1 FROM p_service_schedules s
   WHERE s.service_preference_id = a.service_preference_id
     AND s.deleted_at IS NULL
)
```

- **이유**: 매칭 시도는 누적되므로 1차 실패 후 2차에 성공해도 1차 `FAILED` 레코드는 영구히 남는다. 매칭에 성공하면 `p_service_schedules`에 일정이 생기므로, "일정 레코드가 아예 없는가"로 판정하면 이미 해소된 과거 실패를 자연히 걸러낼 수 있다.
- 재매칭 실패는 기존 일정이 `SCHEDULED`로 복구되어 레코드가 남으므로 이 조건에서 함께 제외된다. 즉 이 API는 **"아직 재매칭이 필요한 초기 매칭 실패"** 만 기본으로 보여준다.

> 참고 : 이 API의 존재로 "초기 매칭 실패 시 결과를 어떻게 확인하는지"가 확정된다 — 사용자는 이 API로 실패 내역을 조회하고, 실패한 건에 대해 16번(재매칭 시도) API를 호출해 재시도한다.
>

## Request

| key | 설명 | value 타입 | 위치 | 제약사항 | Nullable | 예시 |
| --- | --- | --- | --- | --- | --- | --- |
| page | 페이지 번호 | Integer | Query Parameter | `null`이거나 음수면 `0`으로 보정 | O | `0` |
| size | 페이지 크기 | Integer | Query Parameter | `10`, `30`, `50`만 가능, 기본값 `10`. 이 외 값이면 `10`으로 자동 변경 | O | `10` |
| sort | 정렬 | String | Query Parameter | 방향만 파싱(`ASC`/`DESC`), 필드는 `createdAt` 고정. 기본값 `createdAt,DESC` | O | `createdAt,DESC` |
| status | 매칭 결과 필터 | String(ENUM) | Query Parameter | `MATCHED`, `FAILED`만 가능, 미지정 시 `FAILED` | O | `FAILED` |

## Response

| key | 설명 | value 타입 | 옵션 | Nullable | 예시 |
| --- | --- | --- | --- | --- | --- |
| matchingAttemptId | 매칭 시도 ID | UUID | - | X | `3fa85f64-5717-4562-b3fc-2c963f66afa6` |
| servicePreferenceId | 서비스 희망 일정 ID | UUID | - | X | `3f2504e0-4f89-41d3-9a0c-0305e82c3301` |
| provideServiceId | 제공 서비스 ID | UUID | - | X | `94d8e2b6-3f71-4a95-c608-1e7b5d9f2a43` |
| date | 매칭을 시도한 희망 날짜 | LocalDate | - | X | `2026-09-01` |
| preferredTimeSlot | 매칭을 시도한 희망 시간대 | String(ENUM) | `MORNING`, `AFTERNOON` | O | `MORNING` |
| status | 매칭 시도 결과 | String(ENUM) | `MATCHED`, `FAILED` | X | `FAILED` |
| failureReason | 실패 사유 (`status`가 `FAILED`인 경우에만 존재) | String | - | O | `NO_AVAILABLE_PROVIDER` |
| failedAt | 매칭 실패 일시 | **Instant** | - | O | `2026-09-01T09:00:00Z` |
| matchedAt | 매칭 성공 일시 | **Instant** | - | O | `null` |
- `matchingAttemptId`가 응답에 포함되어, 실패 건에 대해 바로 16번(재매칭 시도) API의 Path Variable로 사용할 수 있다.
- 01번은 내부 필터링용 ID를 응답에서 제외했지만, 이 API는 한 응답에 여러 희망 일정의 시도 내역이 섞여 나오므로 클라이언트가 구분할 수 있도록 `servicePreferenceId`/`provideServiceId`를 포함한다.
- `regionId`/`carePlanId`는 클라이언트에 불필요한 내부 참조 ID이므로 노출하지 않는다.
- `MATCHED` 이력은 이벤트 페이로드에 시간대가 없어 `preferredTimeSlot`이 항상 `null`이다.

> ⚠️ **확인 필요 (신규, 2026-09-08)**: `failureReason`은 provider-service가 보낸 값을 가공 없이 그대로 노출한다. provider-service 현재 구현은 사람이 읽는 문장이 아니라 **`NO_AVAILABLE_PROVIDER`라는 코드 문자열 하나**만 보낸다(`ProviderMatchFailedEvent.NO_AVAILABLE_PROVIDER`, 실패 사유는 이 한 종류뿐). 사용자에게 보여줄 문구로 변환하는 주체를 schedule-service로 할지 클라이언트로 할지 정해야 한다.
>

## Status

> ⚠️ **차단 (신규, 2026-09-08)**: **api-gateway 라우트에 `/api/v1/matching-attempts/**`가 등록되어 있지 않다.** schedule-service 라우트는 `/api/v1/service-schedules/**`, `/api/v1/service-results/**`뿐이라 이 API는 게이트웨이를 통해 호출할 수 없다(404). 16번도 같은 문제이며, 게이트웨이 라우트 추가가 필요하다.
>

| status | ErrorCode | response content |
| --- | --- | --- |
| `200` | - | 조회 성공 (없을 시 빈 배열 반환) |
| `400` | `INVALID_PARAMETER` | `status`에 `MATCHED`/`FAILED` 이외의 값 |
| `403` | `AUTH_FORBIDDEN` | `PATIENT` 이외의 역할로 요청한 경우 |
