- **Swagger / OpenAPI**: `springdoc-openapi 3.1.0`은 Spring Boot 4.1.0을 대상으로 빌드된 버전이며 Springdoc 측에서도 Spring Boot 4에 3.x 사용을 안내함. 단, 일부 회귀 이슈가 보고되어 있어 API 문서 생성 결과 검증 필요.

### 계층별 세부 구조

**domain/**
- `entity/` — 핵심 상태·행위를 표현하는 Entity
- `repository/` — Repository 추상화. CQRS 기반으로 책임을 분리한다 (care-plan-service `CarePlanQueryRepository`/`CarePlanCommandRepository`, schedule-service `ServiceScheduleQueryRepository`/`ServiceScheduleCommandRepository` 참고):
  - `repository/query/{도메인}QueryRepository` — 조회 전용 순수 인터페이스
  - `repository/command/{도메인}CommandRepository` — 상태 변경 전용 순수 인터페이스
  - 둘 다 외부 의존성 없는 순수 인터페이스만 위치하며, `JpaRepository` 등을 직접 상속하지 않는다.

**application/**
- `command/` — 상태 변경(Command)에 사용하는 입력 객체
- `query/` — 조회(Query)에 사용하는 입력 객체
- `service/command/` — 상태 변경 유스케이스 구현
- `service/query/` — 조회 유스케이스 구현
- `result/` — 처리 결과 객체
- `facade/` — 여러 유스케이스/서비스를 조합해 하나의 흐름으로 제공 (26/09/02 신규 추가 — 추후 기능 구현 시 필요성 대비)
- `port/` — 외부 시스템 통신 추상화
- `support/` — 공통 지원 기능

> 변경 이력: 기존 `command_service/`, `query_service/` 플랫(flat) 패키지를 `service/command/`, `service/query/`로 통합. `domain/repository`와 동일하게 상위 패키지(`service/`) 아래 command/query로 나누는 패턴을 적용했다 (TEAM CONVENTION 26/09/02 확정 반영).

**infrastructure/**
- `client/` — Feign 등 외부/다른 Service 통신 구현
- `adapter/` — Application Port 구현체
- `persistence/` — JPA/QueryDSL 구현 (`domain/repository`의 CQRS 분리를 그대로 따른다):
  - `persistence/query/{도메인}QueryRepositoryImpl` — `domain/repository/query`의 인터페이스 구현체 (단순 조회는 Spring Data JPA, 복잡한 조회는 QueryDSL)
  - `persistence/command/{도메인}CommandRepositoryImpl` — `domain/repository/command`의 인터페이스 구현체
  - `Spring{도메인}Repository extends JpaRepository<...>`(Spring Data JPA 인터페이스, 기본 CRUD)는 Query/Command로 나누지 않고 이 패키지에 그대로 두며, 위 두 Impl 클래스가 필요에 따라 주입받아 위임한다.

**presentation/**
- `controller/api/` — 외부 Client용 Public API Controller
- `controller/internal/` — MSA 내부 Service 간 통신용 Internal API Controller
- `request/`, `response/` — HTTP 요청/응답 DTO

> 변경 이력: 기존 `api_controller/`, `internal_controller/` 플랫 패키지를 `controller/` 하나로 묶고 그 안에 `api/`, `internal/`로 구분하는 패턴으로 변경했다 (TEAM CONVENTION 26/09/02 확정 반영).

### 원칙

- Domain 간 직접 접근을 지양한다.
- 공통 기능은 global 패키지에서 관리한다.
- Entity는 Controller로 전달하지 않는다.
- Controller는 DTO만 사용한다.

## 3. 코드 컨벤션

### 기본 원칙

- 의미 있는 이름을 사용한다.
- 축약어 사용을 지양한다.
- 하나의 메서드는 하나의 책임만 가진다.
- 코드보다 주석이 많아지지 않도록 한다.
- 불필요한 주석은 작성하지 않는다.

### Naming

| 대상 | 규칙 | 예시 |
|---|---|---|
| Class | PascalCase | `UserService`, `OrderController` |
| Method | camelCase | `createUser()`, `findOrder()` |
| Variable | camelCase | `userName`, `createdAt`, `orderCount` |
| Constant | UPPER_SNAKE_CASE | `ACCESS_TOKEN_EXPIRE_TIME`, `MAX_PAGE_SIZE` |

### DTO 네이밍

| 종류 | 규칙 | 예시 |
|---|---|---|
| Request | 도메인명 + 행동 + Request | `UserCreateRequest`, `OrderUpdateRequest` |
| Response | 도메인명 + 행동 + Response | `UserCreateResponse`, `OrderCreateResponse` |
| Command | 도메인명 + 행동 + Command | `UserCreateCommand`, `OrderUpdateCommand` |
| Result | 도메인명 + 행동 + Result | `UserCreateResult`, `OrderCreateResult` |

### 계층별 책임

- **Entity**: DB 매핑 역할만 수행한다. 비즈니스 로직은 Service에서 수행한다.
- **Controller**: Request Validation → Service 호출 → Response 반환까지만 수행한다.
- **Service**: 비즈니스 로직과 Transaction 관리만 수행한다.
- **Repository**: 단순 CRUD는 Spring Data JPA, 복잡한 조회는 QueryDSL을 사용한다.

## 9. Code Review

### Pn Rule

| Level | 설명 |
|---|---|
| P0 | 즉시 수정 |
| P1 | 반드시 수정 |
| P2 | 수정 권장 |
| P3 | 개선 제안 |
| P4 | 아이디어 |
| P5 | 참고 의견 |

### 리뷰 원칙

- 사람을 리뷰하지 않는다. 코드를 리뷰한다.
- 근거를 함께 작성한다.
- 이미 작성된 다른 팀원의 코드 리뷰 내용도 반드시 확인한다.
- P3 이상부터는 코드 변경 후 approve, P4~5는 변경 없이 approve 가능.

**좋은 예**
```plain text
P2: 예외처리
현재 Optional.get()을 사용하고 있습니다.
orElseThrow()를 사용하는 것이 예외 처리를 명확하게 할 수 있습니다.
```

## 19. Swagger 컨벤션

Controller와 Swagger 문서화 코드를 분리하는 패턴을 아래와 같이 확정한다.

참고: [Swagger 인터페이스를 통해 Controller 코드와 Swagger 코드 분리](https://velog.io/@wjdtn747/Swagger-%EC%9D%B8%ED%84%B0%ED%8E%98%EC%9D%B4%EC%8A%A4%EB%A5%BC-%ED%86%B5%ED%95%B4-Controller-%EC%BD%94%EB%93%9C%EC%99%80-Swagger-%EC%BD%94%EB%93%9C-%EB%B6%84%EB%A6%AC)

- 모든 Controller: `@Tag`
- 모든 API: `@Operation`, `@ApiResponses`
- 필수 작성: Summary, Description, Response

### 확정 패턴

Swagger 어노테이션(`@Tag`, `@Operation`, `@ApiResponses`, `@Parameter` 등)을 실제 `@RestController` 클래스에 직접 달지 않고, **별도 인터페이스로 분리**한다. Controller는 이 인터페이스를 구현(`implements`)하며 `@RequestMapping` 계열 어노테이션과 실제 로직만 가진다.

모든 Controller는 예외 없이 대응하는 `{Domain}ApiSpec`(또는 `{Domain}InternalApiSpec`)을 반드시 `implements`한다. Swagger 어노테이션이 없는 Controller라도 인터페이스 분리 자체는 생략하지 않는다.

- **인터페이스 네이밍**: `{Domain}ApiSpec` (예: `ScheduleApiSpec`)
- **패키지 위치**: Controller와 동일한 위치 — `presentation/controller/api/`, `presentation/controller/internal/` (26/09/02 패키지 구조 변경 반영)
- **적용 범위**: 외부 API(`controller/api`)와 내부 API(`controller/internal`) 모두 동일 패턴 적용

```java
// presentation/controller/api/ScheduleApiSpec.java
// Swagger 문서화 전용 인터페이스. @Tag/@Operation/@ApiResponses는 전부 여기에만 작성한다.
@Tag(name = "Schedule", description = "서비스 일정 관리 API")
public interface ScheduleApiSpec {

    @Operation(summary = "서비스 일정 목록 조회", description = "퇴원 예정자 또는 서비스 제공자가 자신의 서비스 일정 목록을 조회한다.")
    @ApiResponses({
        @ApiResponse(responseCode = "200", description = "조회 성공"),
        @ApiResponse(responseCode = "403", description = "권한 오류")
    })
    ApiResponse<PageResponse<ScheduleListResponse>> getSchedules(
        @Parameter(description = "요청자 ID") UUID userId,
        @Parameter(description = "상태 필터") ScheduleStatus status,
        Pageable pageable
    );
}

// presentation/controller/api/ScheduleApiController.java
// Swagger 어노테이션 없이 순수 매핑/로직만. Validation → Service 호출 → Response 반환.
@RestController
@RequiredArgsConstructor
public class ScheduleApiController implements ScheduleApiSpec {

    private final ScheduleQueryService scheduleQueryService;

    @Override
    @GetMapping("/api/v1/service-schedules")
    public ApiResponse<PageResponse<ScheduleListResponse>> getSchedules(
        @RequestHeader("X-User-Id") UUID userId,
        @RequestParam(required = false) ScheduleStatus status,
        Pageable pageable
    ) {
        return ApiResponse.ok("서비스 일정 목록 조회 성공", scheduleQueryService.findSchedules(userId, status, pageable));
    }
}
```

내부 API(`controller/internal`)도 동일하게 `{Domain}InternalApiSpec` 형태로 분리한다 (예: `ScheduleInternalApiSpec`).

## 20. 코드 작성 원칙

- **SOLID**: 가능한 준수한다.
- **DRY**: 중복 코드를 최소화한다.
- **KISS**: 복잡한 코드보다 단순한 코드를 작성한다.
- **YAGNI**: 필요하지 않은 기능은 미리 구현하지 않는다.
