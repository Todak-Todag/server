# 📋 프로젝트 기획안

> 출처: Notion `기획안` 문서를 200줄 이내로 압축. "추가 논의 필요"로 표시된 항목은 원문 그대로 미확정으로 남김.
> 상세 배경(문제 정의 근거, 페르소나 세부 서사, 시나리오 전문)은 생략했다. 필요 시 원본 Notion 문서 참고.

## 1. 개요

- **프로젝트명**: 퇴원환자 지역사회 케어 플랫폼
- **한 줄 소개**: 병원이 퇴원 예정자에게 필요한 서비스를 제안하고, 퇴원 예정자가 Care Plan을 최종 결정한 뒤 지역 내 서비스 제공자와 연결하여 퇴원 후 돌봄을 지속 관리하는 지역 기반 플랫폼
- **대상 지역** (초기 3개): 전남 고흥군 / 경북 의성군 / 강원 영월군 (고령 인구 비중, 의료 접근성 등을 기준으로 선정)
  - ⚠️ 미확정: 구체적 선정 통계 근거

## 2. 해결하려는 문제

1. 퇴원 후 필요한 여러 서비스(방문간호·방문진료·방문요양·병원동행 등)를 하나의 계획으로 관리하기 어려움
2. 퇴원 시점 계획과 실제 생활 상황이 달라져 추가 돌봄 요구가 발생할 수 있음
3. 서비스 제공자마다 다른 일정을 사용자가 직접 조율하기 어려움
4. 지역마다 이용 가능한 서비스·제공자가 달라 자원 연결이 어려움

## 3. 타겟 사용자 및 핵심 역할

| 사용자 | 주요 역할 |
| --- | --- |
| 퇴원 예정자 | Care Plan 최종 결정, 서비스 신청·변경·취소, 사회복지사 매칭 신청 |
| 병원 담당자 | 퇴원 예정자 등록, 퇴원 일정 등록, 필요 서비스 사전 제안 |
| 사회복지사 | 매칭된 사용자의 Care Plan·일정 관리 지원 |
| 서비스 제공자 | 제공 서비스·가능 일정 등록, 서비스 수행 및 결과 관리 |
| Admin | 담당 지역의 사용자·제공자·Care Plan·서비스 운영 관리 |
| Master | 전체 지역 및 Admin 관리 |

> ⚠️ 미확정: 페르소나 세부 정보(연령·가족구성·질환 등)는 원본 문서에도 미정으로 표시됨

## 4. 핵심 흐름

```
병원 담당자: 퇴원 예정자 등록 → 퇴원 일정 등록 → 필요 서비스 제안
  → 퇴원 예정자: 서비스 확인/선택 → 오전·오후 희망 시간대 선택 → Care Plan 확정
  → 서비스 종류·지역·요일·시간 기준 제공자 매칭 → 일정 확정 → 퇴원
  → 서비스 수행 → 수행 결과 기록
  → (퇴원 후 7일 이내) 추가 서비스 신청 가능
  → (허용 시간 내) 일정 변경/취소 가능
```

- 사회복지사 매칭: 퇴원 전·후 모두 가능, 별도 신청 기한 없음
- 서비스 간 이동/준비 시간은 현재 범위에서 고려하지 않음 (일정 겹치지 않으면 연속 제공 가능)

## 5. 핵심 기능 (도메인별)

- **병원**: 퇴원 예정자/일정 등록, 필요 서비스 제안
- **Care Plan**: 서비스 확인·선택, 희망 시간대(오전/오후) 설정, 확정, 진행 상태 관리, 추가 신청, 변경/취소, 수행 여부 관리
- **매칭**: 서비스 종류·지역·요일·시간·개인 제공자 기준
- **일정**: 제공자 가능 일정 등록, 확정, 변경/취소, 수행 일정 관리 (기본 서비스 시간 1시간 고정)
  - ⚠️ 미확정: 오전/오후 구체적 시각 범위
- **사회복지사**: 매칭 신청/자동 매칭, Care Plan·일정 관리 지원
- **서비스 제공자**: 서비스·지역·요일·시간 등록, 일정 확인, 수행, 결과 관리
- **Admin/Master**: 지역별 운영 관리, 전체 지역/Admin 관리

## 6. MVP 범위

**포함**: 퇴원 전 Care Plan 구성 / 서비스 제공자 매칭 / 서비스 일정 관리(오전·오후, 1시간 단위, 변경·취소) / 퇴원 후 7일 이내 추가 신청 / 수행 여부·미수행 사유 관리 / 사회복지사 매칭 / 서비스 제공자 관리 / 지역별 Admin 및 Master 운영 관리

**제외 (향후 확장)**: 대상 지역 확대, 실제 서비스 기관/의료기관 시스템 연동, 실제 의료·건강 데이터 연계
- ⚠️ 미확정: 확장 기능의 구체적 범위

**제외 (범위 밖, 확정)**: 직접적인 의료행위·진단·처방, 민감 의료 데이터 필수 확보, 실제 의료기관 시스템 연동, IoT/의료기기 데이터 연동

MVP 데이터는 프로젝트 환경에서 관리 가능한 **Dummy Data**로 구성한다.

## 7. 기술 스택

| 기술 | 목적 |
| --- | --- |
| Spring Boot 4.1.1 / Java 21 / Gradle | 백엔드 구현 |
| PostgreSQL 16 | 핵심 영속 데이터 |
| Redis | 캐싱 후보 |
| RabbitMQ | 서비스 간 비동기 이벤트 (✅ 확정) |
| Docker / Docker Compose / AWS EC2 | 실행·배포 환경 |
| GitHub Actions | 빌드·배포 자동화 |
| Eureka / API Gateway / Config Server / Zipkin / Grafana / Prometheus | 인프라 구성 요소 |

> ✅ 확정 (2026-09): 기획안 원문의 "Kafka 후보" 기재는 배경 논의 당시 기록이며, 실제 구현은 RabbitMQ로 확정됨 (`코드_컨벤션.md` 참고).
> 원칙: MSA를 위해 억지로 기능을 분리하지 않는다 / 불필요한 이벤트를 만들지 않는다 / 동기·비동기는 즉시성·결합도·데이터 일관성을 기준으로 판단한다.
> ⚠️ 미확정: 기술별 구체적 적용 범위(동기/비동기 기준 세부화)

## 8. 프로젝트 범위

**포함**: 퇴원 예정자·일정 관리, Care Plan 구성/확정, 지역 기반 제공자·일정 관리, 매칭, 일정 관리(변경·취소·수행결과), 사회복지사 매칭, 지역별 Admin/Master 운영, Dummy Data 기반 운영

**제외**: 실제 의료행위·진단·처방, 실제 의료기관 시스템 연동, IoT/의료기기 연동, 실제 외부 서비스 제공기관 시스템과의 직접 연동
- ⚠️ 미확정: 외부 기관·시스템의 구체적 연동 범위

## 9. 성공 기준

**기능**: 병원 담당자의 등록/제안 → 사용자 최종 결정 → 매칭 → 일정 확정 → 수행 → 결과 기록까지 전체 흐름이 동작 / 변경·취소가 정해진 기준(24시간)에 따라 처리 / 취소된 서비스는 삭제되지 않고 미수행 상태·사유로 관리 / 사회복지사 매칭 가능 / 지역별 Admin·Master 운영 가능

**기술**: 핵심 서비스 정상 실행 / 서비스 간 통신 정상 처리 / 서비스별 데이터 소유권 준수 / 비동기 이벤트 정상 처리 / 핵심 비즈니스 데이터 일관성 보장 / 장애·이벤트 관측성 확보 / CI/CD로 빌드·배포 가능
- ⚠️ 미확정: 구체적 성능 수치, 가용성/장애 복구 목표

## 10. 프로젝트 차별점 (요약)

- 퇴원 전부터 퇴원 후까지 하나의 Care Plan으로 연결
- 병원은 제안만, **최종 결정은 사용자**가 함
- 퇴원 후 7일 이내 추가 서비스 신청 등 **변경 가능한 Care Plan**
- 복잡한 시간 대신 오전/오후 단순 선택 + 사회복지사 지원 옵션
